# BUG 2026-11-17

## BUG-2026-11-17-01：QQ 内切换到泰深输入法时 QQ 崩溃（MSVCP140.dll）

**严重级别**：P0（第三方宿主进程被输入法拖崩，用户直接丢会话）

**发现方式**：Eric 在 QQ 里切换输入法，QQ 弹出崩溃提示，错误模块 `MSVCP140.dll`。
微信、网页、游戏内未复现。

### 现象

QQ 崩溃报告：

| 字段 | 值 |
|------|-----|
| 错误模块 | `MSVCP140.dll` |
| 模块路径 | `versions\9.9.16-29927\resources\app\MSVCP140.dll` |

宿主侧实测版本（`Get-ChildItem -Recurse` 读文件版本信息）：

| 位置 | MSVCP140 版本 |
|------|--------------|
| QQNT 根目录 | 14.29.30154（VS2019） |
| `versions\9.9.16-29927\` | 14.29.30154 |
| `versions\9.9.16-29927\resources\app\` | 14.29.30154 |
| QQScreenShot\Bin* | 14.32 / 14.38 |
| 本机 System32 | **14.51.36247**（VS18，即本仓库编译工具链） |

### 根因

输入法 DLL 用 MSVC 14.51 编译，默认 `/MD` 动态链接 CRT，导入表声明
`MSVCP140.dll` / `VCRUNTIME140.dll` / `VCRUNTIME140_1.dll`。

Windows 加载器解析导入表时，对**同名模块直接复用进程中已加载的那一份**，
不会因为路径不同而另加载系统目录里的新版本。QQ 是 Electron 应用，启动时已把
自己 `resources\app` 下的 14.29 载入进程；泰深 DLL 一被加载，14.51 编译的
C++ 标准库调用就落到 14.29 的实现上——ABI 不匹配，崩在 `MSVCP140.dll`。

微信/网页/游戏不崩，是因为它们的程序目录没有自带旧版 CRT，加载器回落到
System32 的 14.51。

这同时暴露一个隐性问题：**用户机器没装新版 VC 运行库时，输入法根本无法加载**
（安装脚本此前不部署 CRT redist）。

### 修复

改为**静态链接 MSVC CRT**，让 DLL 完全不再导入 `MSVCP140.dll` 家族：

1. `platform/windows/CMakeLists.txt`
   - `cmake_policy(SET CMP0091 NEW)`（必须在 `project()` 之前，否则变量被忽略）
   - `set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>")`
     → 编译选项 `-MT`

2. 仓库根 `.cargo/config.toml`（新建）
   ```toml
   [target.x86_64-pc-windows-msvc]
   rustflags = ["-C", "target-feature=+crt-static"]

   [target.i686-pc-windows-msvc]
   rustflags = ["-C", "target-feature=+crt-static"]
   ```

C++ 与 Rust 必须同时静态，否则 `libcmt` / `msvcrt` 混链会 LNK2005。

**安全性前提**：静态 CRT 会让 DLL 拥有独立堆，跨 DLL 边界释放内存会崩。
核对 FFI 契约——`engine_text.h` 全部是「调用方分配缓冲、引擎写入」的两阶段
协议（`read(nullptr, 0)` 查容量 → `read(buf, n)` 读正文），`ffi.rs` 中
grep 不到任何 `*mut c_char` 返回值、`CString::into_raw`、`mem::forget`。
没有任何 Rust → C++ 的堆所有权转移，静态 CRT 安全。

### 验证

`dumpbin /dependents` 四份产物全部消失动态 CRT 依赖：

| 产物 | 依赖数 | 动态 CRT |
|------|-------|---------|
| taishen_ime.dll | 17 | 无 |
| taishen_ime_x86.dll | 17 | 无 |
| taishen_ime_imm32.ime | 12 | 无 |
| taishen_ime_imm32_x86.ime | 12 | 无 |

剩余依赖全部是 Windows 系统 DLL（kernel32 / user32 / d2d1 / dwrite / imm32 等）。

- `cargo test --release -- --test-threads=1`：全部通过
- `test_tsf_load.exe`：`CoCreateInstance ITfKeyEventSink OK`
- 64 位进程 `LoadLibrary` 加载 `taishen_ime.dll` 与 `taishen_ime_imm32.ime`：成功

### 踩坑记录

- **构建前必须确认 `engine/src/lib.rs` 稳定**。并行开发时 cargo 会读到文件
  被部分写入的中间态，报出与眼前源码不符的错误（实测：`cannot find value
  KEEP_EXACT`，而磁盘上该行已是 `keep_exact`）。
- **PowerShell 管道会吞掉退出码**：`cargo build ... | Select-Object -Last N`
  后 `$LASTEXITCODE` 未必反映 cargo 的真实结果，判断成败要看输出里的
  `Finished` / `error` 或显式写 `"EXIT=$LASTEXITCODE"`。
- `test_imm32_load.exe` 报 `GetLastError=193` 是历史缺陷，与本次改动无关：
  x64/x86 两套测试 exe 输出到同一个 `out` 目录，x86 构建把 exe 覆盖成 32 位，
  而它加载的是 64 位 `.ime`。
