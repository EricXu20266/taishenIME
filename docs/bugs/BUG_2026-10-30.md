# BUG 2026-10-30

## BUG-2026-10-30-01：设置页保存后不生效（配置热加载全线下线）

**现象**：设置 → 按键 → 候选词导航，勾选「小键盘 + / −」点确定后，小键盘 `+` 仍上屏 `+`，
不翻页；其它按键设置同样要重启宿主应用才生效。

**根因**：`0.1.67` 停用托盘图标（commit `d4065f1`）后托盘窗口不再创建，`m_trayHwnd`
恒为 `nullptr`。而 `StartConfigWatch()` 把 `m_configPath` 的初始化放在
`m_trayHwnd == nullptr` 的提前 `return` 之后：

```cpp
if (m_configWatchStarted || m_trayHwnd == nullptr) return;  // ← 永远命中
m_configPath = GetDllDir() + L"config.ini";                 // ← 永远不执行
```

于是 `m_configPath` 恒为空 → `ReloadConfigIfChanged()` 开头即 `return` →
`OnKeyDown` 里的按键级热加载彻底失效。

**日志实证**（`%LOCALAPPDATA%\TaishenIME\ime_debug.log`）：

| 时间 | 进程 | 记录 |
|------|------|------|
| 20:48:52 | 12456 | `Settings: config saved` |
| 20:48:53 | 5472 | `ReloadConfigIfChanged: config.ini 已变更，热重载完成`（旧 DLL，仍有托盘窗口） |
| 20:48:55 | 12456 | `OnKeyDown vk=107 eff=187 eat=T committed=测试下+`（新 DLL，未重载 → 走标点） |

即：只有还持有旧版 DLL 的进程能热重载，新进程读不到新配置。

**修复**：

- `platform/windows/src/tsf_module.cpp`：`StartConfigWatch()` 改为无条件初始化
  路径与基准 mtime，托盘窗口判断只决定是否挂 2s 定时器；无定时器时由按键检查兜底
- `ApplyConfig()` 增加 `pageKeys minus_equal/numpad/brackets/comma_period` 日志
- `platform/windows/src/imm32/imm32_ime.cpp`：`ImeSelect()` 补 `SetKeyBindings()`——
  IMM32 进程没有 TSF 的 `ApplyConfig`，键位设置此前恒为默认值，老应用里同样不生效

**验证**：

- `test_config_reader.exe`：新增 `key_page_extra=minus_equal,numpad` 解析断言 → 通过
- `test_ascii_mode.exe`：STEP1–STEP10 全部通过
- CMake Release 全目标编译通过（仅既有 `/EHs`→`/EHa` 警告）

**遗留**：

- 候选单页时按翻页键没有任何视觉反馈（候选窗 V0.3.x 已移除 `1/3` 页码指示），
  容易被误判成「不生效」；验证请用多候选拼音（如 `shi` / `zhong`）或把候选数调大
- `HandleKeyDown` 翻页分支注释写「翻不动再往下走标点」，但 `Engine::page()` 在边界
  返回的是当前页候选数（非 0），那句降级分支实际不会执行；吞键到底仍是无反应

## BUG-2026-10-30-02：用户热词被同前缀旧词压住（别名/全拼合并丢精确判定）

**现象**：Eric 反馈「用户热词好像不工作」。实测用户词库里「会话」今天用过 134 次
（拼音键 `huih`），打 `huih` 首选却是「绘画」（同一键，22 次，72 天前）。「直接」被
「之间」压到第 2 位，同一模式。抽查 25 个高频用户词，23 个在首位，2 个失败。

**根因**：同一个词可能同时存在两种学习记录——规范全拼（`huihua`→会话）与简拼别名
（`huih`→会话）。加载时 `add_user_entry()` 在前缀键 `huih` 下按词合并（频率累加、
`last_used` 取最新），但条目里的「完整拼音长度」字段 `e.3` 只保留**首次插入**的值：

```rust
if let Some(existing) = entries.iter_mut().find(|(w, _, _, _)| *w == word) {
    existing.1 = existing.1.saturating_add(frequency);
    existing.2 = existing.2.max(last_used);
    // existing.3 未更新（保持首次的 6 = "huihua".len()）
}
```

`query()` 的精确层判据是 `e.3 == key_len`。别名键 `huih`（len 4）下，会话的 `e.3`
仍是 6 → 不进精确层，落到前缀扩展层；而「绘画」的 `e.3` 是 4，留在精确层 →
精确层永远排在扩展层前面，热词被旧词压住。

**修复**：

- `engine/src/dictionary/mod.rs` `add_user_entry()`：合并分支改为
  `existing.3 = existing.3.min(pinyin_str.len())`——别名本身就是用户打过的完整
  拼音串，应视为精确

**验证**：

- 新增 `engine/tests/user_word_alias_exact.rs`：先学 `huihua`→会话、再学 `huih`→会话、
  并放入同前缀竞争词 `huih`→绘画，断言会话在首位。修复前 `Some(1)` 失败，修复后通过
- 真实用户词库快照（3536 条）25 个高频词首位命中 25/25（修复前 23/25）

**顺带排查（非缺陷）**：Eric 同时反馈「组词 `zuoge` 不工作」。用户词库与 8/16 备份
里都没有「做个」这条记录；`ime_debug.log` 20:54:01 显示按 PageDown 已进入组词模式
（候选切成单字「做/作/坐/左/座」），随后退格两次退出，改为分两次上屏「做」+「个」，
整词学习未触发。引擎侧用真实词库跑完整组词流程（翻页 → 选「做」→ 选「个」）后
`zuoge → 做个` 立即落库且回到首位，机制正常。可改进点：组词入口只有翻到候选末尾
才触发，进入后无提示，退格即退出。

**独立审计**（code-auditor，只读）：0 个 P0/P1，3 个 P2，结论为改动可采信。

- P2-1 `user_short_index` 的 `.3 = min` 是空操作——该索引只按频率排序、从不读第四元组
  → 已删除该 hunk（避免后来人误以为简拼索引也参与精确层判定）
- P2-2 测试补「规范全拼键 `huihua` 下仍首位」断言，`set_user_dict_path(None)` 前移到
  断言之前，失败时不残留临时库路径
- P2-3 `SELECT` 无 `ORDER BY` 的顺序依赖：`min` 可交换，已消除对该顺序的依赖；
  其余同频 tie 顺序与 `canonical_pinyin_for_word` 遍历 HashMap（lib.rs:842-848）为既有
  问题，不在本次范围
