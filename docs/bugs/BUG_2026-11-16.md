# BUG 2026-11-16

## BUG-2026-11-16-01：houxuan 首候选被邻键纠错「勾选」抢占

**严重级别**：P0（常用双字词被另一条拼音的词挤到第 4 位，属于选词错误）

**发现方式**：Eric 输入 `houxuan`，首位出现「勾选」而不是「候选」。

### 现象

| 输入 | 修复前首位 | 修复后首位 |
|------|-----------|-----------|
| houxuan | 勾选 | 候选 |
| zhongguo | 中过 | 中国 |
| zhonggou | 中够 | 中国 |

### 根因（两条独立）

1. **邻键纠错插队**：`h` 与 `g` 键盘相邻，`correction_variants("houxuan")` 生成
   `gouxuan`，命中常用词「勾选」。旧逻辑只判断「首位是否常用词」——
   「候选」不在常用词表，于是纠错结果 `insert(0)` 抢到首位。
2. **整句解码污染双音节输入**：`zhongguo` 可切成 `zhong+gu+o`（3 音节），
   整句通道解出「中过」插到首位，把词频 4298 的「中国」压到第 3。

### 修复

- `lib.rs` 邻键纠错前置判据：精确候选（`Source::Dictionary`）里已有常用词时，
  纠错结果追加在精确命中之后，不再插队。
- `lib.rs` `apply_word_len_match`：完整拼音输入下纠错来源不享受常用词加权，
  且整体退到长词组；新增「首选切分字数」维度（houxuan 2/3 音节两种切法时，
  3 字词不得压过 2 字首选词）。
- `sentence.rs` 整句下限改按**最短切分**判断，不足 3 音节不进整句通道。

### 验证

`candidate_fix` 新增 5 条断言：houxuan / 勾选不進前 3 / zhongguo / zhonggou / nihap。
长句整句候选（`nimenjigezaizheliganshenme`）行为未退化。

## BUG-2026-11-16-02：组词阶段数字透传（多翻几页冒出「12」）

**严重级别**：P1（选字过程中往正文写入无意义数字）

**发现方式**：Eric 报「组词输入时多翻几页就带出 12」。0.1.73 曾修过一次（越界数字键吞噬），复测仍在。

### 现象

输拼音 → 翻 3 页自动进组词 → 按 1 选首字 → 继续选字 → 正文里冒出 `12`。

### 根因

`apply_mode(Mode::Compose)` 的候选首位是「一次吃光全部剩余音节的整词」。用户按 1 以为在选首字，实际选中整词：`select_candidate` 里 `advance = 词字符数` → `compose_idx` 直接推到末尾 → `reset()` 清空拼音与候选。之后按下的数字既不满足 `engine_in_compose()`、也不满足「有拼音」，`ShouldEatKey` / `HandleKeyDown` 双双判定透传，宿主把它们当普通字符写进正文。

0.1.73 修的是「按数字但该页没有对应候选」这条支路，与本现象无关——已实测确认（`step11` 用例仍通过，而现场仍能复现）。

### 修复

`Mode::Compose` 末尾重排：首位固定为当前音节单字（`chars().count() == 1`），整词候选保留第 2 位起。逐字推进后 `compose_idx` 只加 1，组词不结束，后续数字仍在输入法手里。

### 验证

- 修复前离线复现（`test_ascii_mode` STEP12）：`pick1[0]` 后 `compose=0 pinyin_len=1`，数字键 `eat=0`、`eatTest=0`，`digit_passthrough=1`。
- 修复后：`pick1[0]` 后 `compose=1 remain=[guo]`；组词中数字 `eat=1 eatTest=1`；`digit_passthrough=0`。
- 引擎全量 `cargo test --release --lib`：379 passed / 0 failed / 5 ignored。

## 遗留-01：phrase_group_guess 拆不出「这个我们的」

**状态**：未修复（2026-10-29 之后长期失败，非本轮引入）

### 现象

`zhegeweomende` → 「这个瓦恶偶闷得」等噪声；期望「这个我们的」。
`zhegewimende`（单字符误按）可正常拆出。

### 根因

- 系统词库没有「我们的」三字词（只有「我们」women 4199），必须拆成「我们」+「的」。
- 段级纠错只覆盖**单字符替换**；`weom → wom` 需要「e/o 换位 + 漏 n」组合编辑，不在覆盖范围。

### 修复方向

扩展段级纠错到「一次换位」或「换位 + 漏字」组合；需控制递归预算，避免长串爆炸
（历史上 `GROUP_NODE_BUDGET` 就是为此加的）。

## 遗留-02：zhyang 混合输入不命中「张扬」

**状态**：未修复（非本轮引入）

### 现象

输入 `zhyang`（zh 声母 + yang 全拼），候选只有「装 / 状 / 传 / 这样 / 支阳」，
词库里的「张扬」（zhangyang 2041）不可达。

### 根因（两层）

1. **suffix_index 桶截断**：`dictionary/mod.rs:698` 每桶截断 `MAX_PREFIX_ENTRIES = 400`。
   以 `yang` 结尾的词条有 1364 条，桶内按「声母串长度优先、再按词频」排序，
   `zh`（两字符声母）排在单声母之后，张扬被挤出前 400。
2. **补充分支被数量门槛挡住**：`lib.rs:2461` 附近 `query_abbrev_full` 的调用条件为
   `candidates.len() < page_size * max_pages`。`zhyang` 的前缀噪声已占满 5 个候选，
   abbrev 分支根本没有执行。

### 修复进展

- **索引层：已修（2026-11-16）**。桶内排序改为词频优先（原「声母串长度优先」把
  两字符声母 zh/ch/sh 整体排到单声母之后）。重建 `system_dict.db.bin` 后实测
  `query_abbrev_full("zhyang")` 已含「张扬」（第 10 位）。
  副作用：`xzai` 这类高频长词（逍遥自在）在 abbrev 池中前移，首位「现在」不变；
  全量回归 377 passed / 3 failed，无新增失败。
- **管道层：未修**。`lib.rs` 中 `query_abbrev_full` 的调用条件仍是
  `candidates.len() < page_size * max_pages`；`zhyang` 的前缀噪声占满 5 个候选后
  分支不执行，即使执行也会被 `truncate` 截断。要真正可达需要重新设计
  「混合输入结果 vs 前缀噪声」的优先级，历史上该区域有回归教训。
