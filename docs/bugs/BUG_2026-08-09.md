# Bug 修复记录 — 2026-08-09

## BUG-2026-08-09-01: 测试挂起 60s+（0.4.5 拆分组词相关测试）——根因是 .bin 缓存缺失，不是递归爆炸

**现象**：`cargo test` 全量运行卡死，日志停在 `test_group_exact_phrase_priority`，
60s+ 无输出被 bash 超时杀掉。初判为 `group_rec` 递归组合爆炸。

**排查过程**（关键：不要轻信初判）：
- 第一轮判断"递归爆炸"→ 加了 `(rest, errs)` 记忆化 → **引入新 bug**：
  同一 `(rest, errs)` 在不同 segs 前缀下展开结果不同（seg 组合不同），visited 会误伤
  正确路径——实测丢失「这个我们的」（`test_group_wim_to_wom` 失败）
- 对比验证：原始代码 + release 模式 group 测试 **0.87s 通过** → 递归本身不爆炸
- 真正根因：`system_dict.db.bin` 预编译缓存缺失（gitignore，部署期生成），
  debug 模式 from_sqlite 全量构建 62 万词条 × 5 个索引 > 60s 被杀
- 证据链：`dict exists: true` + `bin exists: false` → init_blocking 卡在 from_sqlite

**修复**（engine/src/dictionary/mod.rs）：
- 用 release 模式 `build_index` 生成 `resources/system_dict.db.bin`（7.9s），加载秒级
- `group_rec` 加节点预算 `GROUP_NODE_BUDGET=5000`（防御性：词库继续扩容后
  full_index 命中面增大，无记忆化递归仍可能指数爆炸；预算内穷尽、耗尽即放弃）
- **弃用 visited 记忆化**——设计上有缺陷（见上），预算方案零误伤

**教训**：
1. 测试挂起 ≠ 代码无限循环。先确认资源加载路径（.bin 缓存缺失是最常见的伪装者）
2. 记忆化缓存 key 必须包含所有影响结果的输入维度；`(rest, errs)` 不完整时宁可不缓存
3. gitignore 的部署期产物（.bin）缺失会导致测试环境行为与生产完全不同

## BUG-2026-08-09-02: ffi_integration zhonggou 纠错不出「中国」——两个叠加根因

**现象**：`zhonggou（完整拼音）应纠错出 中国` 断言失败。
correction_variants("zhonggou") 生成正常（含 zhongguo 变体），query("zhongguo")
首位就是「中国」，但引擎最终候选里没有。

**根因 A：deletion 变体灌满候选**（engine/src/lib.rs）
- `zhonggou` 的 deletion 变体 `zhonggu` 命中 364 词，全量灌入 candidates
- candidates 超过 `page_size`(5) 后，correction 分支条件 `candidates.len() < page_size`
  为 false → 被跳过
- 而「中国」只能靠 correction 变体 `zhongguo`（精确命中、query 首位）补入——
  deletion 的 `zhonggu` 前缀命中里中国排第 30+ 位，被 truncate 截断

**根因 B（隐藏最深）：V0.5 动态组词误触发**
- 修好根因 A 后「中国」进了候选（pos 14），但测试仍失败
- ffi 测试遍历候选时翻页：`page()` 里 `page_advances >= 2`（b0d8a59 阈值）
  即触发组词模式 → `query_all()` 重算候选为组词单字 → 中国被替换
- 完整拼音候选充足（19 候选 4 页）时，翻 2 页只是浏览候选，不应误入组词

**修复**（engine/src/lib.rs）：
- 三个纠错分支（spelling/deletion/correction）变体补入限量 `CORR_TAKE=3`
- correction 分支条件放宽 `page_size` → `page_size * max_pages`（最终兜底仍有机会）
- 组词翻页阈值 2→3（保留「候选翻完立即触发」逻辑）；同步更新
  `test_compose_entry_after_2_pages`（改用真实词库 + 3 次翻页断言）和
  `test_compose_entry_short_pinyin`

**教训**：
1. 候选补入分支必须限量——一个变体命中 364 词全量灌入，会撑爆后续分支的
   page_size 判断（典型的"先来的撑死，后来的饿死"）
2. 修好一个 bug 后测试仍失败，可能是**第二个独立 bug**——用 DEBUG 打点
   确认每个阶段候选内容，比反复猜更快
3. 新功能（组词模式）改全局行为（翻页触发）时，必须回归所有翻页遍历的旧测试

## BUG-2026-08-09-03: test_radical_mode_basic 并行 flaky——radical 全局表竞争

**现象**：`cargo test --lib` 并行执行时 `test_radical_mode_basic`（ushuishou 应有拆字候选）
偶发失败；单独跑 + 串行模式（`--test-threads=1`）100% 通过。

**根因**：radical 模块用全局 `static RADICAL: Mutex<Option<HashMap>>`。
两个测试并行竞争同一全局表：
- `test_radical_mode_basic` / `test_radical_select_no_learn`：`init(Some(path))` 加载表
- `test_radical_mode_unknown_empty`：`init(None)` 清空表
- 执行顺序不定：unknown_empty 后跑会清掉 basic 已加载的表 → 查询读空表失败

**修复**（engine/src/radical.rs + lib.rs）：
- radical.rs 加 `#[cfg(test)] pub(crate) static TEST_LOCK: Mutex<()>`
- 三个 lib.rs 测试 + 三个 radical.rs 内部测试入口持锁串行执行

**教训**：
1. 全局可变状态（Mutex<Option<...>>）被多个测试读写时，必须有测试级串行锁
2. flaky 测试的标准三连验证：单跑 → 串行全量 → 并行全量（多次），定位竞争窗口
3. `cfg(test)` 锁不影响生产代码，是纯测试基础设施

## 会话级排查经验（跨三个 bug 的共性）

1. **bash 输出截断陷阱**：cargo test 全量输出在 PowerShell/cmd 管道下多次截断
   （日志停在中间、无 test result 汇总行）。对策：重定向到文件 + 单独跑各测试目标
   （`cargo test --test X`），不要依赖管道过滤看结果
2. **DEBUG 打点是排查引擎行为的最快路径**：在关键分支加 eprintln，确认
   "分支是否执行 / 候选是否进入 / 何时被移除"，比推理代码更快收敛
3. **stash 对比验证预存 bug**：怀疑修改引入回归时，`git stash` 后跑同一测试，
   若同样失败则为预存问题——避免改错方向
4. **gitignore 产物缺失**是环境与生产行为差异的高发源（.bin 缓存、.dbe 临时文件）
