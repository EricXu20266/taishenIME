# BUG 2026-11-15

## BUG-2026-11-15-01：魔兽世界组词时拼音漏进输入框、翻页无组合区、长词选不到

**严重级别**：P1（游戏内组词完全不可用，且会往聊天框写入拼音）

**发现方式**：Eric 在魔兽世界中输入 `moshoushijizhenhaowan`，逐字选词时
输入框出现「天qi'zhen'hao气zhen'hao真hao好」这类内容；翻页后组合区空白；
期望的「魔兽世界」始终选不到。

**影响范围**：所有不渲染 TSF 组合属性的宿主（GFx 自绘引擎类游戏，
魔兽世界经 msctfscape 桥接实测复现）。普通应用（记事本 / 浏览器 / 微信）不受影响。

---

## 现象

| 序号 | 现象 | 复现输入 |
|------|------|----------|
| 1 | 选完第一个字后，剩余拼音被当正文插入 | `tianqizhenhao` → 选「天」→ 输入框出现 `天qi'zhen'hao` |
| 2 | 每次选字都重复一次「已选字 + 剩余拼音」 | `天qi'zhen'hao` → `气zhen'hao` → `真hao` → `好` |
| 3 | 翻页后编辑区没有组合串，候选窗也可能看不到内容 | 组词中按 PgDn / +/- |
| 4 | 一翻页就掉进逐字模式，长词永远选不到 | `moshoushijizhenhaowan` 只有 2 页候选，翻第 2 次即进组词 |

## 根因（三条，各自独立）

### 1. `inline_preedit` 开关只接了候选窗，没接应用文档

- 候选窗侧：`candidate_window.cpp:127` 用 `!m_inlinePreedit` 决定画不画拼音行 ✅
- TSF 侧：`tsf_module.cpp:2088` 无条件把拼音写进 composition ❌
- IMM32 侧：`imm32_ime.cpp:578` 无条件写 `GCS_COMPSTR` ❌

于是关掉 `inline_preedit` 也拦不住拼音进文档。

魔兽世界不渲染 TSF 组合属性，`StartComposition("qi'zhen'hao")` 的 `SetText`
被当成正文插入。日志实证：`ReplaceCompositionText: len=5 text=shi'b`
（带音节分隔符，只有 `syllable_display()` 会产出这种串）。

### 2. 组词中间选字用「Commit + Start 剩余音节」

`tsf_module.cpp:2143` / `2583` 在组词中间音节选字后调用
`Op::Start` 重新开组合并写入剩余音节。宿主若把组合当正文，
第 2 次、第 3 次选字就会继续插入拼音。

### 3. 引擎翻到候选末尾就强制进组词，且组词只出单字

- `engine/src/lib.rs` `page()`：`if self.page_advances >= 3 || at_boundary`
  ——候选只有 1-2 页时，翻一次翻不动就进组词。
- `apply_mode(Mode::Compose)`：候选硬过滤 `chars().count() == 1`，只出单字。

用户还没浏览完候选就被拽进逐字模式，而逐字模式本身也出不了长词。

## 修复

### A. 行内预编辑贯通到文档组合串

新增 `AppStateInlinePreeditEnabled(cfg)` / `AppStateInlinePreeditForProcess(cfg, proc)`：

判定顺序 `app_inline`（强制开）> `app_no_inline`（强制关）>
出厂兼容表（`wow.exe`）> 全局 `inline_preedit`。

| 文件 | 改动 |
|------|------|
| `include/config_reader.h` | 新增 `app_no_inline_list` |
| `src/config_reader.cpp` | 解析 / 写回 `app_no_inline=` |
| `include/app_state.h` | 两个判断函数声明 |
| `src/app_state.cpp` | 出厂表 `kBuiltinNoInline = {wow.exe}` + 判定实现 |
| `src/tsf_module.cpp` | 组合串只在 `inlinePreedit` 为真时写入；组词中间音节不再 Start 剩余拼音；候选窗 `SetInlinePreedit` 与文档同源 |
| `src/imm32/imm32_ime.cpp` | 新增 `g_inlinePreedit` 与 `GetSelfProcessName()`；组合串恒空 |

### B. 组词触发与候选

- `page()`：删掉 `at_boundary` 单次触发，只保留累计 3 次翻页。
- `apply_mode(Mode::Compose)`：候选改为
  `phrase_group_guess(剩余拼音)` 的整句/整词（优先）+ `query(当前音节)` 的词条与单字（兜底）。
- `select_candidate`：组词候选按字符数推进音节（选「魔兽世界」一次走完 4 个音节）。

## 第二轮：候选窗被自己的兜底判据藏掉（同日 14:10）

第一次修复后 Eric 实测：拼音不再漏进输入框，但「翻页后屏上没内容」依旧。

**日志证据**（Wow PID 22224，`ime_debug.log`）：

- 全程无 `ReplaceCompositionText` → 拼音污染已修好
- 有 `UpdateCandidateWindow: UpdateUIElement`，但**没有** `pinyin=... cands=...`
  → 在 `UpdateCandidateWindow` 的自绘兜底分支提前 `return`

**根因**：`msctfime` 桥接会替游戏读一次候选数据（`GetCount`/`GetString`），
把 `m_uiElementDataRead` 置 1。`AppStateShouldSelfDrawWhenSuppressed` 的自动判据
「宿主读过数据 = 它会自己画」因此判 true → `CandWin().Hide()` → 用户看不到任何候选。
而 Wow 是自绘引擎，实际并不画。

**修复**：新增出厂强制自绘表 `kBuiltinSelfDraw = { wow.exe }`，
优先级 `app_self_draw` > `app_no_self_draw` > 出厂表 > 自动判据。

## 纠错三项缺陷（同日 17:30，引擎层）

### 现象（release 构建 + 真实词库实测）

| 输入 | 应出 | 修复前位置 |
|------|------|-----------|
| `nihap` | 你好 | 第 14 位（第 3 页） |
| `keyyi` | 可以 | 第 11 位 |
| `weti` | 问题 | 第 8 位 |
| `meiganxi` | 没关系 | 完全不出 |
| `xinashi` | 显示 | 第 2 位，首位是冷僻的「希腊式」 |

### 根因（三条独立）

**1. 纠错结果被词长分区压后**

`apply_word_len_match` 用输入串估算目标词长。`nihap` 切不干净，被估成 3 字输入，
于是 3 字冷僻词（尼哈番 / 逆函数）占满第一组，2 字的「你好」被降组。

邻键纠错块已经把「你好」插到第 0 位，随后被这一步挪到第 14 位。

**2. 缺「漏打字母」变体**

原变体生成只有三类：邻键替换、相邻换位、删除（多打）。没有插入。

`meiganxi` → 没关系 需要 `gan → guan`（插入 u），属于青简的 `TypoKind::Missing`
那一类，泰深完全没有对应能力。

**3. 触发判据用候选数量，不是输入质量**

三个纠错块都按 `candidates.len() < page_size(*max_pages)` 触发。输入一旦前缀命中
足够多的词（`zhongg` 443 条），纠错整块跳过。青简用的是 `unlikely_pinyin`
（切不干净，或非末尾音节残缺/简拼）。

### 修复

| 位置 | 改动 |
|------|------|
| `engine/src/correction.rs` | 新增 `insertion_variants`：每个位置插一个字母，只留「插入后能完整切分且首音节不变」的变体，上限 24 |
| `engine/src/lib.rs` `query_all` | 新增插入变体分支，排在邻键纠错之后，条件为「输入不像话 + 前 3 位无常用词」 |
| `engine/src/lib.rs` `apply_word_len_match` | 分区排序键：`Source::Correction` 且是常用词的候选不参与词长分组 |

插入变体必须排在邻键纠错之后——`xinashi` 的邻键纠错已给出「显示」，再跑插入是纯浪费
（实测 30ms → 180ms）。

## BUG-2026-11-16-01：组词时已选字从组合区消失，重新选字后又冒出来

**严重级别**：P1（组词过程中看不到已选内容，用户失去方向）

**现象**（Eric 在 Notepad++ 复现）

| 序号 | 操作 | 现象 |
|------|------|------|
| 1 | 组词中选首字 → 退格 | 已选字从组合区消失；重新选字并输出后，之前消失的字又出现 |
| 2 | 组词中选首字/首词 → 翻页 | 翻页本身正常 |
| 3 | 组词中翻页后选后面的字 | 只看到当前音节，已选字看不到 |

### 根因：组合串有 6 个拼装点，其中 3 个丢了已选前缀

组合串语义本应是「已选前缀（`m_composeAccum`）+ 待选后缀（引擎剩余音节）」，但拼装散落在：

| 位置 | 拼装内容 | 是否含已选前缀 |
|------|---------|---------------|
| 键盘中间选字 | `accum + syllable` | ✅ |
| 鼠标点击选字 | `accum + syllable` | ✅ |
| 状态变化（输入/翻页/退格穿透） | **只有 `syllable`** | ❌ |
| 退格 | `accum + syllable`（仅 compose_undo 成功时） | ⚠️ 失败时穿透到上面那行 |
| 候选窗拼音行 | **只有 `syllable`** | ❌ |

翻页、退格后状态变化都会走「状态变化」分支，用剩余音节覆盖整段组合串 →
已选字从组合区消失。而 `m_composeAccum` 仍在内存里，下一次选字
`accum + syllable` 又把旧字拼回来 → 「重新选字后旧字又出现」。

现象 3 同源：候选窗拼音行只显示剩余音节，翻页选后面的字时看不到已选内容。

### 第一次修复（已推翻）：只统一了拼装点

把 6 处拼装收敛到 `BuildCompositionText` + `SyncComposition`，但已选前缀仍由
平台层 `m_composeAccum` 维护副本。实测出现三个新问题：

| 现象 | 原因 |
|------|------|
| 退格后候选变回完整拼音，再选字首字重复两次 | 引擎已回退 `compose_idx`，平台副本没同步回退 |
| 选完所有字后只输出尾词 | 为防残留加的 `RefreshState` 清理在最终提交前就把副本清了 |
| 翻页后候选窗拼音行仍只有剩余音节 | 副本与引擎状态分叉 |

### 最终修复：引擎做唯一状态源

| 层 | 改动 |
|----|------|
| `engine/src/lib.rs` | 新增 `compose_prefix()`（已选词汉字串）；`select_candidate` 在组词最后一个音节返回**整词**（reset 前一次给全） |
| `engine/src/ffi.rs` | 新增 `engine_compose_prefix` |
| `include/engine_bridge.h` / `engine_text.h` | 函数声明 + `ReadEngineComposePrefix` |
| `src/tsf_module.cpp` | 删除 `m_composeAccum`；`BuildCompositionText` 改为「引擎前缀 + 剩余音节」；所有 Start/Update/Commit 走 `SyncComposition` |

组词态的组合串不再有平台层副本，每次显示都从引擎读前缀——引擎回退、选字、
reset 之后显示自动一致，不存在两份状态分叉的可能。

### 引擎语义变化

`select_candidate` 在组词最后一个音节由「返回最后选中的字」改为「返回整词」。
平台层直接提交返回值，不再自己拼前缀（引擎 reset 后前缀不可读）。

### 验证

- `cargo test --lib compose`：9 通过 / 0 失败
- 待 Eric 实机确认：退格回退不重复、翻页/选后续字能看到已选、最终输出无尾字重复

### IMM32 路径（同轮补齐）

LOL / 老程序走 `taishen_ime_imm32.ime`，原先组词是「逐字上屏」且组合串只有剩余音节。
`imm32_ime.cpp` 对齐 TSF：

| 改动 | 说明 |
|------|------|
| `GetDisplayPinyinWide` | 组词态 = 已选前缀 + 剩余音节 |
| `ImeToAsciiEx` | 中间音节不提交，只更新组合串；最后一个音节提交引擎返回的整词 |
| 组词态退格 | 先回退已选词（`compose_undo`），无已选才删拼音字母 |
| 候选窗拼音行 | 与组合串同源（含前缀） |
| 鼠标点选 | 中间音节不落文档，只重写组合串；最后音节提交整词 |

IMM32 与 TSF 现在共用同一套引擎状态（`compose_prefix` / `compose_undo`），
差异只在「组合串怎么写进宿主」这一层。

## 连带修复：有副作用的 FFI 被读了两遍

### 现象

「选了首字就再也选不动后面的字」，按数字键/空格/翻页全部透传。

### 根因

`ReadEngineUtf8` 的流程是「先调一次查容量 → 再调一次读正文」。它只适用于**无状态读接口**。
而 `engine_select_candidate` / `engine_compose_undo` / `engine_take_char` 每调用一次
就推进引擎状态，于是：

```
第 1 次（查容量）：选中「折」，compose_idx 0→1
第 2 次（读正文）：又选一次「格外哦闷得」，compose_idx 直冲末尾 → 组词结束
```

按一次数字键实际选了两个音节，`engine_in_compose()` 变 0，之后所有候选键判定失败透传。

日志实证（`ime_debug.log`）：

```
OnKeyDown vk=50 committed=折     ← 第一次成功
OnKeyDown vk=50 eat=F            ← 第二次开始全部 eat=F
（其后数字键 / 空格 / 翻页全 eat=F）
```

同一问题也影响：`engine_compose_undo`（日志里 `undone=` 恒为空，动作空白执行）、
`engine_take_char`（以词定字一次取两个）。

### 修复

`platform/windows/include/engine_text.h` 新增 `ReadEngineActionUtf8`：
固定 512 字节缓冲、**只调一次**，专供有副作用接口使用。

| 接口 | 读取方式 |
|------|---------|
| `engine_select_candidate` | `ReadEngineActionUtf8`（有状态） |
| `engine_compose_undo` | `ReadEngineActionUtf8`（有状态） |
| `engine_take_char` | `ReadEngineActionUtf8`（有状态） |
| 候选 / 拼音 / 前缀 / 音节串 | `ReadEngineUtf8`（无状态，保持两步读） |

### 验证（实机日志 01:45）

```

01:45:22.683  ComposeBackspace prefix=珐 undone=珐
01:45:22.683  text=fa's'w'da'e'wa       ← 退格回退到完整拼音
01:45:25.043  compose=N text=fa's'w'da'e'w  ← 无已选时退格删拼音
01:45:26.274  Commit text=发散瓦大额外   ← 一次提交、无重复
```
