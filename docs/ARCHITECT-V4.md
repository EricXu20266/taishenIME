# 泰深输入法架构 V4 —— 进程边界重构

> 本文是结构性规划，不是实施计划。定的是「谁在哪、边界在哪」，
> 具体分支由结构推导出来。
> 前置：`docs/ARCHITECT.md`（v3.1，现行结构）、
> `docs/modules/engine-process-isolation/DESIGN.md`（问题记录与实测）

---

## 〇、一句话

**TSF DLL 只保留「只能在宿主进程内做」的两件事，其余全部进程外。**

现行结构把引擎、词库、D2D 渲染、设置页、语音全塞进一个会被复制进几十个宿主进程的
DLL 里。这不是代码质量问题，是**边界划错了**。

---

## 一、为什么必须重构（不是假设，是实测）

2026-11-17 任务栏搜索里三条独立故障，全部指向同一个结构缺陷：

| 故障 | 直接原因 | 结构层面为什么必然发生 |
|------|---------|----------------------|
| 切到泰深卡 43 秒 | `user_dict_db_path()` 回退 `%APPDATA%`，容器内 SQLite 打开阻塞 | DLL 直接持有词库与 IO，每次进新宿主都要重新初始化 |
| 候选窗不出现 | `CreateWindowExW` + D2D 初始化在 AppContainer 内阻塞 | 渲染代码在宿主进程里，容器环境不允许它工作 |
| 空格上屏卡 22 秒 | `RequestEditSession(TF_ES_SYNC)` 在沉浸式宿主跨进程文本存储上同步等待 | 上屏走同步会话，把宿主的跨进程延迟直接暴露到 UI 线程 |

前两条换个宿主（容器、商店应用、UWP）就会复发；第三条在 Win11 新记事本、任务栏搜索
这类沉浸式应用里必然发作。**修一条不能改善另外两条**——因为它们不是同一个 bug。

对照三家同类产品，没有一家把渲染放在宿主进程的 TSF DLL 里：

| 产品 | TSF DLL 体积 | 渲染在哪 |
|------|-------------|---------|
| 同类产品① | 952 KB（壳）+ 2.2 MB（core） | 独立进程内的 `ui.dll` |
| 同类产品② | 424 KB | 不在 TSF DLL 内 |
| 系统自带输入法 | 系统组件 | 系统 CoreUI |
| **泰深** | **7.3 MB（12782 行 C++ + 静态链接引擎）** | **宿主进程内自绘** |

## 二、结构判据：什么「不可委托」

划边界的依据不是「哪部分代码多」，而是**API 契约强制要求它在哪里执行**。

| 动作 | 能否外移 | 判据 |
|------|---------|------|
| `ITfKeyEventSink::OnKeyDown` 收键 | ✗ 不可 | COM 接口只能由宿主进程内的 TIP 实例实现 |
| `ITfContext` 写组合串 / 上屏 | ✗ 不可 | 编辑会话绑定宿主文档，跨进程无句柄 |
| 光标屏幕矩形测量 | ✗ 不可 | `GetTextExt` / `GetGUIThreadInfo` 需要宿主上下文 |
| 查词、排序、整句解码 | ✓ 可 | 纯计算，输入输出都是值 |
| 候选窗渲染 | ✓ 可 | 窗口归属与输入法逻辑无关 |
| 词库加载、用户词持久化 | ✓ 可 | 文件 IO |
| 语音采集与转写 | ✓ 可 | 设备与网络 |
| 设置页、状态横幅、语言栏图标 | ✓ 可 | 与输入链路解耦 |

**只有前三条留在 DLL 里。** 现在这三条之外的所有东西都在 DLL 里。

## 三、目标结构

```
┌─ 宿主进程 A ────────────────┐
├─ 宿主进程 B ────────────────┤   taishen_ime.dll / taishen_ime_x86.dll（向薄演进）
├─ 宿主进程 C ────────────────┤     ├─ ITfKeyEventSink：收键 → 同步查询 / 镜像快速判定
└─ 32 位宿主 ─────────────────┘     ├─ ITfContext：异步写组合串/上屏
                                    ├─ 光标矩形测量 → 发消息
                                    └─ 过渡期：非容器普通宿主保留进程内回退
                     ↕  命名管道 \\.\pipe\taishen-ime-render
┌─ taishen_server.exe（单实例 Local\TaishenIMEServerSingleInstance）─┐
│  ├─ 引擎状态机 + 词库 + 排序 + 学习（engineMutex 串行保护）          │
│  ├─ 候选窗渲染（D2D/DWrite，ui_* 控件库；Program Files 支持 uiAccess）│
│  └─ 过渡期：设置窗口 / 状态横幅 / 托盘 / 语音仍在宿主按需承载          │
└────────────────────────────────────────────────────────────────────┘
```

**IMM32 通道（`.ime`）同样瘦身**：它复用同一套 server，
自身只保留 `ImeProcessKey` / `ImeToAsciiEx` / 组合串上屏。

## 四、为什么是「一个 server」而不是两个

同类产品的做法是把引擎与渲染放在同一个进程，没有再拆开。我们采用同样的粒度，理由：

1. **候选与渲染是毫秒级同步关系**。拆两个进程要多一次转发，
   每一页候选都要两跳；
2. **状态一致性**。候选窗要知道「当前页是哪个引擎结果」，跨进程维护这份对应关系
   是额外复杂度，收益接近零；
3. **uiAccess 可以后加**。候选窗需要盖过高 z-band 宿主时要 `uiAccess`，
   那要求代码签名 + 装 Program Files。这是**部署问题，不是结构问题**，
   不影响「一个 server」的边界。

**代价**：server 崩溃时输入法整体不可用。缓解是 DLL 侧超时降级
（详见 §七）。

## 五、通信协议要点

| 项 | 决定 | 理由 |
|---|---|---|
| 传输 | 命名管道 `\\.\pipe\taishen-ime-render`（重叠 IO，64 并发上限，首帧 5s / 中途帧 1s / 服务端写 200ms 超时） | 零注册，32/64 位通吃，防单连接卡死或句柄耗尽 |
| 编码 | 4B LE 长度前缀（`<= 64KB`）+ UTF-8 JSON 帧（严格定宽整数界限校验） | 与现有 Rust/C++ 生态一致；`CandidateMeta`（`tier`/`reasons`/`score`）与 `SkipValue` 容错解析 |
| 主操作集 | `ping`/`pong`、`key_input`/`candidate_list`、`commit`、`show`/`move`/`hide`/`reload`、`error` | `pong` 携带 `dictReady`/`entries`/`build`/`uiAccess`/`band`/`traditional`/`shuangpin`；`key_input` 含 `flags` 显式覆盖位 |
| 会话标识 | `(宿主 PID, TextService 实例 ID)` + 内核 `GetNamedPipeClientProcessId` 校验 | 同一应用可能有多个输入上下文；禁止客户端伪造 `hostPid`、`show` 额外校验前台/归属 |
| 按键往返 | 同步请求，总预算 **≤ 50ms**；DLL 持有轻量 `RemoteEngineMirror` 判定 `ShouldEatKeyRemote` 与普通选词即时上屏 | 超时立刻断管并透传不吞键，避免卡顿宿主 UI |
| 候选与上屏 | `key_input` 同步返回当页候选（含 `committed`），`commit` 异步落盘学习；DLL 在本进程内异步写文档 | 减少阻塞；异步会话防沉浸式宿主卡顿 |
| 渲染 | **不经过 DLL**（普通宿主远程失败时可局部降级） | server 自己画，DLL 只报物理像素光标矩形 |

**AppContainer 访问与窗口层级补充约束（V1–V4，目标：任务栏搜索/商店应用可用 + 终端用户免重启无缝升级）**：

1. **V1 · 容器 DLL 只连不拉**：AppContainer 进程调用 `CreateProcess` 产生的子进程会继承容器令牌，导致 server 同样被困在容器内。因此 `taishen_server.exe` 必须由普通权限进程拉起（用户登录自启任务 / 任意普通宿主内的 DLL 首次激活）；容器内 DLL 检测到未连接时仅尝试连管道，**绝不拉起进程，也不回退进程内引擎/D2D**，连接失败直接透传按键。
2. **V2 · 管道与 DLL 最小权限**：
   - 命名管道与单实例互斥量创建时动态获取当前用户 `TokenUser` SID 构造 DACL（不再开放宽泛 `AU`）：仅授权 `SY`、`BA`、`OW`、当前用户 SID、`AC`（`S-1-15-2-1`）与 `LPAC`（`S-1-15-2-2`）读写，并附带低完整性 SACL（`S:(ML;;NW;;;LW)`），使容器进程可直连；
   - 安装器仅对 `taishen_ime.dll` / `taishen_ime_x86.dll` 二进制本身授予 `S-1-15-2-1:(RX)` 和 `S-1-15-2-2:(RX)`（以便任务栏搜索等容器宿主加载 DLL），日志与 `config.ini` 不授权；引擎外移（D3）后词库文件在容器内也不再被访问。
3. **V3 · 高 z-band 遮挡（`uiAccess`）**：任务栏搜索（SearchApp）运行在高于普通桌面窗口的 z-band，候选窗需要 manifest `uiAccess="true"` 才能稳健覆盖。`uiAccess` 要求二进制带受信任签名且安装于受保护目录（`%ProgramFiles%\TaishenIME`）：
   - 个人/本地验证阶段：安装器生成自签证书导入本机 `LocalMachine\Root` 并签发 `taishen_server.exe`，装入 `Program Files` 即可零成本验证；若无管理员/签名失败，`install_latest.ps1` 降级启动普通目录 server，确保功能可用；`%LOCALAPPDATA%\TaishenIME\taishen_server.exe` 启动时若检测到 `Program Files` 版存在会主动让位；
   - 公开发布阶段：切换为受信任商业代码签名证书。
4. **V4 · 协议向后兼容与终端用户免重启升级契约**：
   - **Windows TSF 客观约束**：覆盖安装无法卸载已映射进运行中宿主进程的旧 DLL（「旧 DLL + 新 Server」混跑是商用输入法升级后的必然常态），终端用户必须装完即用，不得要求重启应用或电脑；
   - **主协议版本冻结在 `v=3`**（`kRenderIpcVersion = 3`）：后续功能只通过 JSON 可选字段 / 能力位增量演进，解码器以 `SkipValue()` 忽略未知键，禁止因纯增量字段升主版本号；
   - **服务端多版本向下兼容协商**：Server 接受 `[kMinSupportedIpcVersion = 2, kRenderIpcVersion = 3]`，以首帧版本号锁定该连接协议 `connVersion`，回包 `pong`/`candidate_list` 的 `"v"` 按 `connVersion` 回填，缺失的 v3 可选字段（如 `flags`）取安全默认值 `0`，全部安全校验保持一致；仅拒绝 `< 2`（如 `v1`）、`> 3` 或连接中途擅自切换版本号的帧。

**关键点：渲染路径上不再有 DLL。** 这条决定了容器内不会再撞 D2D 建窗阻塞。

## 六、会话模式：必须异步

`RequestEditSession` 不得带 `TF_ES_SYNC`。

依据：沉浸式应用（任务栏搜索、Win11 新记事本）的文本存区隔着进程边界，
同步会话会让调用方一直等。同类产品的源码注释里明确写了这条约束。

改造影响：`tsf_module.cpp` 现有的两处同步调用
（读选区、组合操作）都要改成「发起会话 → 回调里继续」。
这会改变上屏流程的控制流，是全项目风险最高的一处改动，
必须单独一轮做、配完整回归（记事本 / 浏览器 / QQ / 微信 / 游戏各测一遍）。

## 七、生命周期与降级

| 场景 | 行为 |
|---|---|
| 首次激活，server 未运行 | 普通宿主：DLL 拉起来，冷却/熔断保护下异步或短超时握手；AppContainer 宿主：**只连不拉**（server 由登录自启 / 普通宿主拉起），连不上直接透传 |
| 覆盖安装后老进程（旧 v2 DLL + 新 v3 Server） | Server 按首帧 `connVersion=2` 向下兼容应答，旧 DLL 忽略新增可选字段，候选与渲染无缝可用，**终端用户免重启** |
| server 崩溃或连续失败 | 管道断开进入指数短探测退避（`50/150/500/1500/5000 ms` 逐级收敛）并直通按键；普通宿主重拉起，连续 5 次失败熔断 5 分钟（容器内仅重连不拉起） |
| 词库加载中（`dictReady=0`） | Server 放行 `key_input` 并限频记日志；客户端 1s 窗口内零 IPC 透传，到期自动重探恢复 |
| 远程渲染发送失败（`SendShow`/`SendMove` 失败） | **非 AppContainer 普通宿主自动降级回退本地 `m_candidateWindow` 绘制**（远程恢复成功时自动隐藏本地窗防双窗）；AppContainer 宿主严守 V1 约束不回退本地 D2D |
| 真正不兼容版本（`< 2` 或 `> 3`） | Server 回 `version_mismatch` 拒绝；客户端持久化置位 `m_protocolMismatch`（仅握手成功清零），`ShouldEatKeyRemote` 即使有残留拼音/组词态也一律直通不吞键，每 30 秒探活一次、60 秒限频记日志；普通宿主仅允许自愈重启更低版本旧 server，严禁杀死高版本 server |
| server 空闲 | 保留（输入法使用时长短、频率高，冷启动代价大于常驻内存） |

**DLL 里不再有引擎，所以「引擎延迟销毁」这类问题自然消失**——
引擎生命周期归 server 自己。

## 八、迁移路径：四步，每步独立可停

| 步 | 内容 | 独立收益 | 风险 | 状态 |
|---|------|---------|------|------|
| **1** | 异步编辑会话（`tsf_module.cpp` 两处去 `TF_ES_SYNC`） | 修掉沉浸式宿主/容器上屏 22 秒卡顿 | 中：改上屏控制流 | **✅ 已实现（0.1.77）** |
| **2** | 候选窗外移（`taishen_server.exe` + `\\.\pipe\taishen-ime-render` AC/LPAC/LW 管道 + DLL `(RX)` ACL + 登录自启） | 容器内零 D2D 阻塞、候选窗进程外绘制；可选 `tools/enable-uiaccess.ps1` 覆盖高 z-band | 中：新增进程与协议 | **✅ 已实现并通过 IPC 冒烟（0.1.77）** |
| **3** | 引擎外移（D3 + 加固 + 兼容升级） | 容器宿主零本地词库/引擎；状态跨宿共享；支持 `v2`/`v3` 向下兼容与失配零吞键、普通宿主默认开启并保留 `config.ini` `=0` 逃生开关 | 高：协议定型与安全加固（已完成 F1–F10 + 向下兼容） | **✅ 核心已实现，普通宿主已默认切至 `use_server_* = true`（V2.2，灰度中）** |
| **4** | 删除进程内回退路径 & DLL 瘦身 | 普通宿主默认全面切至 `use_server_engine`，DLL 移除 `taishen_engine.lib` 与 D2D 依赖，拆分约 4470 行 `tsf_module.cpp`，将横幅/托盘/设置/语音迁入 server，达到终态体积 | 中：需全宿主长稳回归后再剥离 | ⬜ 待启动 |

**为什么是这个顺序**：

- 第 1 步不依赖 server，可以立刻做，且是后两步的前提
  （server 渲染出的候选要靠异步会话写进文档）；
- 第 2 步只需要「候选数据 + 光标矩形」这一条协议，配合 V1–V3（登录自启 + 管道 DACL + DLL `(RX)` + `uiAccess`），即可让任务栏搜索与商店应用像主流输入法一样正常出候选；
- 第 3 步的前置「候选结构体化（`tier`/`reasons`/`score`）」已于 2026-11-20 完成，D2 稳定后即可无缝衔接。

**每步的验收只看一件事**：容器或沉浸式宿主里，那一条故障是否消失。

## 九、结构推导出的分支

定完结构，工作分支是自然长出来的：

| 结构决策 | 长出的工作分支 |
|---|---|
| DLL 只保留收键 / 写文档 | `tsf_module.cpp` 按职责拆分；删除 DLL 内的配置应用与候选窗更新 |
| 渲染移入 server | `ui_*.cpp`（13 个）+ `candidate_window` + `banner` + `theme` 整体迁出，**代码原样复用** |
| 引擎移入 server | 新增协议 crate；`engine_bridge.cpp` 的 50 个 FFI 调用改为消息 |
| 异步编辑会话 | `tsf_composition.cpp` 重构；上屏从「同步拿结果」改为「指令驱动」 |
| 32 位宿主 | 协议与位数无关；`taishen_ime_x86.dll` 保持独立产物 |
| 容器 / 沉浸式宿主 | 单独一条验证分支（任务栏搜索、商店应用、Win11 记事本） |

**渲染层迁出时不要重写**：`ui_*` 控件库与主题系统都是平台无关的 Win32 + D2D，
搬进程只需要换窗口宿主，逻辑一行不用改。

## 十、收益与代价

**收益**

1. DLL 从 12782 行降到 3000 行量级，不再链接引擎与 D2D；
2. 容器 / 沉浸式宿主可用（三条故障同时消失，不用逐条修）；
3. 引擎状态跨宿主共享——现在每个宿主进程各有一份 Engine；
4. 崩溃面收敛到「收键 + 写文档」两个动作；
5. 候选窗可独立加 `uiAccess` 盖过高 z-band 宿主。

**代价**

1. 每次按键一次 IPC 往返（本机管道 0.1–0.3ms，相对候选查询 <5ms 可接受）；
2. 生命周期管理（server 拉起、崩溃重连、协议版本）；
3. 迁移期保留进程内回退路径一个版本；
4. 第 1 步会改动**所有宿主**的上屏路径，需完整回归。

## 十一、不做什么

| 不做 | 理由 |
|---|---|
| 拆两个 server（引擎 / 渲染分家） | 候选与渲染是毫秒级同步关系，拆开每页多一跳，收益为零 |
| 云候选 / LLM 候选 | 与纯本地定位冲突 |
| 多引擎实例或多用户 | 单机单用户，没有场景 |
| 重写渲染层 | 现有 `ui_*` 与主题系统可直接复用 |
| 一次性完成四步 | 每步都可独立验证，一次做完无法定位回归 |

## 十二、结构验收判据

看 DLL 侧的依赖与行为，不看功能列表：

| 判据 | 检查方式 |
|---|---|
| DLL 不依赖 D2D / DWrite | `dumpbin /dependents` 看不到 `d2d1.dll` / `DWrite.dll` |
| DLL 不依赖 SQLite / 引擎 | 无 `taishen_engine.lib` 链接记录 |
| DLL 体积 | 目标 < 500KB（现在 7.3MB） |
| 容器内可切换 | 任务栏搜索里切到泰深，不假死 |
| 容器内可出候选 | 候选窗可见（由 server 绘制） |
| 容器内可上屏 | 空格上字无延迟 |
| 切换耗时 | < 50ms（引擎不在 DLL 里，无需初始化） |

## 十三、代码组织与模块边界

结构定下来之后，代码摆放必须跟着定，并且**能自动检查**。
不能只写在文档里靠自觉——今天的 `tsf_module.cpp` 3506 行混着四类职责，
就是没有边界约束的结果。

### 13.1 目标目录

```
engine/                      纯 Rust，平台无关，禁止任何 Windows 依赖
  src/                       拼音引擎：切分、词库查询、排序、整句
  tests/exam-cases.tsv       候选质量断言（考试用例）
  examples/exam.rs           考试工具

crates/taishen-protocol/     新增：IPC 协议（纯 Rust，无 Windows 依赖，可单测）
  src/                       消息定义 + 编解码，DLL 与 server 共用

platform/windows/
  src/tsf/                   薄：收键、写文档、光标测量（迁移目标）
  src/imm32/                 薄：同上，IMM32 通道
  src/ui/                    渲染（迁移目标：搬进 server，代码原样复用）
  src/config/                配置读写（迁移目标：搬进 server）
  include/                   FFI 与共享头

server/                      新增：taishen_server.exe
  src/                       引擎装配 + 候选窗宿主 + 设置 + 语音
```

> 注：当前过渡期代码仍位于 `platform/windows/`（如 `include/render_ipc.h`、`src/taishen_server.cpp`、`src/ipc_render_client.cpp`、`src/tsf_module.cpp`）；第 4 步完成后再按上述目标目录落盘并接入结构门禁。

### 13.2 边界规则（每条都要能检查）

| 规则 | 为什么 | 检查方式 |
|---|---|---|
| `engine/` 不得依赖 Windows crate | 引擎必须能被 macOS / Linux 壳复用 | `cargo tree -p taishen_engine` 无 `windows*` |
| `crates/taishen-protocol` 不得依赖 `platform/` | 协议要两端共用，不能绑任何一端 | `cargo tree` 只出现 serde |
| `src/tsf/` 不得 `#include <d2d1.h>` / `<dwrite.h>` | 渲染必须进程外 | `grep` 源码目录 |
| `src/tsf/` 不得链接 `taishen_engine.lib` | 引擎必须进程外（第 3 步后） | `CMakeLists` 链接项 + `dumpbin` |
| 渲染代码只出现在 `src/ui/` 与 `server/` | 防止再次渗回适配层 | 目录检查 |
| `platform/windows/src` 单文件 ≤ 1000 行 | 3506 行的 `tsf_module.cpp` 是反例 | 脚本统计 |

**这些规则建议做成一个 `tools/check-structure.ps1`**，接进 `package.ps1` 前置校验。
不是文档承诺，是构建门禁。

### 13.3 开发流程（从今天的过程里提炼）

| 约定 | 由来 |
|---|---|
| **结构性改动先改 ARCHITECT-V4，再动代码** | 今天的教训：先改代码再补文档，路线图与实现脱节 |
| **同一安装目录只有一个部署方** | 今天两个会话并发部署，测到的不是最新改动 |
| **构建前确认源码 mtime 稳定（> 20 秒）** | 撞过 cargo 读到半写状态的 `lib.rs` |
| **每次改动跑 exam + 冒烟测试** | 考试工具能覆盖人工验证不到的候选回归 |
| **容器 / 沉浸式宿主单独列回归项** | 普通应用正常不代表容器内正常，反之亦然 |
| **判断成败看输出内容，不看 `$LASTEXITCODE`** | PowerShell 管道会吞退出码 |

### 13.4 已知陷阱（续写）

| 陷阱 | 正确做法 |
|---|---|
| 日志两次采样的间隔 ≠ 操作耗时 | 要测耗时就在操作前后各打一条 |
| 独立 EXE 探针通过 ≠ 真实宿主可用 | 探针只验证引擎逻辑；TSF 行为必须在真实宿主验证 |
| `EnumWindows` 返回 0 窗口 ≠ 窗口被遮挡 | 0 表示没创建，先分清这两件事 |
| 单条故障修好后不回归相邻路径 | 上屏路径改动必须全宿主回归 |
| 升协议主版本号会导致已加载旧 DLL 的常驻进程失配失灵 | 主版本号冻结（`v=3`），增量字段走可选键；已发版本变更须服务端按连接向下兼容，不得逼用户重启 |
