## 〇、总体定性结论（五维全景评估）

在开源/个人自研输入法坐标系里，`taishenIME` 已完成了极具含金量的核心底座攻坚（静态 CRT 隔离、零拷贝词库 mmap、Trie 拼音切分、异步 TSF 会话与 AppContainer 进程外渲染服务）；但**对照主流商业输入法（搜狗拼音 / 微软拼音 / 微信输入法 / Rime+雾凇成熟方案）**，它目前整体处于**「系统工程底座强 Beta + 交互手感与易用性细节尚有断层 + 整句准确率存在模型代差」**的阶段（五维加权成熟度约 **62%**）。

商业输入法的胜负手由**五大支柱**共同决定——任何单一维度做到 90 分都无法掩盖另一维度的 50 分短板：
1. **维度 A · 系统工程底座与交付安全**（当前 **55%** → 目标 **95%**）：极小零污染注入壳、OS TSF 标准契约、IOCP 高并发自愈服务、正式签名与标准多用户安装交付；
2. **维度 B · 使用手感与微交互（Hand-Feel）**（当前 **62%** → 目标 **92%**）：拼音内编辑光标与可见反馈、候选键盘游走、页码可感、数字后标点衔接、首帧不闪跳；
3. **维度 C · 易用性与全场景体验（Usability）**（当前 **60%** → 目标 **90%**）：分项可控模糊音、竖排候选与主流键位预设、密码/网址框免配自适应、图形化词库管理；
4. **维度 D · 全链路性能与资源治理（Performance）**（当前 **72%** → 目标 **95%**）：消除 D2D 每键百次文本布局重建、`bigram` 零拷贝、去 UI 线程同步 I/O、端到端 P99 进 120Hz 帧预算；
5. **维度 E · 输出质量与评测体系（Output Quality）**（当前 **65%** → 目标 **88%**）：清洗失真试卷、建立 KSPC/Top-K/稳定性/误伤率多维盲测集、突破长句一元惩罚与虚实词倒挂、防误学污染。

## 三、维度 B 深度评估——使用手感与微交互（Hand-Feel）

“手感”决定用户连续输入 1,000 字后的疲劳感与“跟手度”。走查 [tsf_keyevent.cpp](../platform/windows/src/tsf_keyevent.cpp)、[tsf_module.cpp](../platform/windows/src/tsf_module.cpp)、[tsf_composition.cpp](../platform/windows/src/tsf_composition.cpp)、[candidate_window.cpp](../platform/windows/src/candidate_window.cpp) 与 [lib.rs](../engine/src/lib.rs)，定位以下 5 项核心断层：

### 3.1 【P0】预编辑拼音内光标“盲移”与中间插入跳回末尾 Bug
- **代码实证**：
  1. **输入跳回末尾**：[engine/src/lib.rs#L1141-L1143](../engine/src/lib.rs#L1141-L1143) 中 `process_key` 无视 `self.cursor`，永远执行 `self.pinyin_buf.push(...)` 并强制将 `self.cursor = self.pinyin_buf.len()`。用户按 `Shift+Tab` 将光标移动到拼音中部、退格删错字母后重新补打时，新字母会追加到整串最末尾而非光标处。
  2. **光标位置零视觉反馈**：`engine_get_cursor_pos` 在 `platform/windows/` 全目录 **0 处调用**；[tsf_composition.cpp#L343](../platform/windows/src/tsf_composition.cpp#L343) 永远执行 `pRange->Collapse(ec, TF_ANCHOR_END)`；[candidate_window.cpp#L315-L322](../platform/windows/src/candidate_window.cpp#L315-L322) 在非行内模式下绘制 `m_pinyin` 时也未绘制光标竖线 `|`。用户按 `Tab`/`Shift+Tab` 后完全不知道光标目前停在哪个音节上。
  3. **方向键与 Home/End 失效且存在死代码**：[tsf_keyevent.cpp#L243-L350](../platform/windows/src/tsf_keyevent.cpp#L243-L350) 的 `EvalEngineKeyEat` 对 `VK_LEFT`/`VK_RIGHT`/`VK_HOME`/`VK_END` 返回 `false`（直接透传给宿主编辑器导致破坏组合状态或光标跑出输入框），致使 [tsf_module.cpp#L3148-L3155](../platform/windows/src/tsf_module.cpp#L3148-L3155) 成为不可达死代码。
- **升级方案**：
  - 将 `Engine::process_key` 改为在 `self.cursor` 字节边界处 `insert(self.cursor, ch)` 并自增 `self.cursor += 1`（同步处理 `raw_input`）；
  - 在 `EvalEngineKeyEat` 与统一按键状态机中接管有拼音时的 `VK_LEFT`/`VK_RIGHT`（单字符移动）、`Ctrl+Left/Right` 与 `Tab/Shift+Tab`（音节边界移动）、`VK_HOME`/`VK_END`（跳至首尾）；
  - 通过服务端 `CandidateListResponse` / FFI 暴露 `cursorPos`，在 `tsf_composition.cpp` 按字符偏移设置选区光标，并在候选窗拼音行绘制 1px 主题色光标线。

### 3.2 【P0】候选高亮焦点锁死为 `0`，方向键无法游走选词
- **代码实证**：`CCandidateWindow::SetSelectedIndex` 在 [tsf_module.cpp](../platform/windows/src/tsf_module.cpp) 和 [imm32_ime.cpp](../platform/windows/src/imm32/imm32_ime.cpp) 中均为 **0 次调用**，[tsf_module.cpp#L4093](../platform/windows/src/tsf_module.cpp#L4093) 硬编码 `cmd.selectedIndex = 0`。虽然点击 `↓` 能展开 5 列多行网格，但用户无法用方向键在候选之间移动高亮并用 `Space`/`Enter` 确认，必须低头找数字键或伸手摸鼠标。
- **升级方案**：
  - 建立明确的候选高亮导航规则：
    - **单行横排态**：支持 `↓` 展开多行（或在配置为“方向键选词”时 `←`/`→` 移动 `selectedIndex`）；
    - **多行展开态 / 竖排态**：`↑`/`↓`（及多行网格下的 `←`/`→`）实时移动 `m_selectedIndex`，自动跨页翻页；按下 `Space` 提交当前 `m_selectedIndex` 候选，数字键 `1–9` 仍直接选本页第 1–9 项。

### 3.3 【P1】“数字后小数点直通”在实际直敲数字场景下完全失效（`3.14` 变 `3。14`）
- **代码实证**：[tsf_keyevent.cpp#L20,L286-L289,L561-L564](../platform/windows/src/tsf_keyevent.cpp#L20) 通过 `g_lastCommitEndsWithDigit` 实现“数字后紧跟 `.` `,` 出半角小数点/千分位”。但该标志**仅在 IME 自己提交文本时更新**（[tsf_module.cpp#L2370,L3119,L3245](../platform/windows/src/tsf_module.cpp#L3119)）。而中文模式下直接按主键盘或小键盘 `0–9` 键走的是**透传**（[tsf_keyevent.cpp#L824](../platform/windows/src/tsf_keyevent.cpp#L824) 返回 `false`），`g_lastCommitEndsWithDigit` 根本不会置 `true`！实测在中文模式下直接敲 `3` 再敲 `.`，结果仍输出 `3。`。
- **升级方案**：
  - 在 `OnKeyDown` / `HandleRemoteKeyDown` 观察到数字键（主键盘无 Shift `0..9` 或 `VK_NUMPAD0..9`）透传给宿主时，立即置 `g_lastCommitEndsWithDigit = true`；遇非数字、非 `.`/`,`/`:` 键（如空格、回车、字母、退格、焦点切换）自动复位；
  - 扩展覆盖 `:`（紧跟数字后输出半角 `:`，满足 `14:30` 时间与 `16:9` 比例输入）。

### 3.4 【P1】候选窗缺页码指示与 Shift/大写边界质感不足
- **代码实证**：
  1. [candidate_window.cpp#L93,L287-L383](../platform/windows/src/candidate_window.cpp#L287-L383) `CandidatePanel` 接收了 `m_page` 和 `m_totalPages`，但 `Draw` 全程未渲染页码（如 `1/5`）或 `‹ ›` 翻页指示，导致用户翻页完全处于“盲操作”状态。
  2. [config_reader.h#L80](../platform/windows/include/config_reader.h#L80) 注释写 `单按 Shift（<300ms）`，而 [tsf_module.cpp#L3207](../platform/windows/src/tsf_module.cpp#L3207) 实际硬编码 `dur < 500`，且未区分左/右 Shift；Shift 切英文时对已有拼音一律自动上屏原串（[#L3219-L3247](../platform/windows/src/tsf_module.cpp#L3219-L3247)），缺少“丢弃未完成拼音直接切英文”可选策略。
- **升级方案**：在候选窗右上角或末尾渲染 `m_theme.dim` 色的轻量页码/翻页微按钮（支持鼠标点击翻页）；配置页开放「Shift 键位（左右均可 / 仅左 / 仅右）」与「Shift 切换时未上屏拼音处理（上屏字母 / 清空）」。

### 3.5 【P1】异步光标首帧跳动与 Win11 DWM 原生圆角质感缺失
- **代码实证**：
  1. [tsf_module.cpp#L4056-L4063](../platform/windows/src/tsf_module.cpp#L4056-L4063) 在首次按下拼音键且 `GetCaretRectFromContext` 返回异步 `TF_S_ASYNC`（无历史 `m_lastCaretRect`、Win32 GUI caret 失败）时，直接用当前鼠标指针坐标 `GetCursorPos` 显示候选窗；几毫秒后 `OnCaretRectResolved` 到达再重定位到光标处，肉眼可见明显的“从鼠标位置瞬移跳回输入框”。
  2. [candidate_window.cpp#L550-L554](../platform/windows/src/candidate_window.cpp#L550-L554) 每次定位都调用 `CreateRoundRectRgn` + `SetWindowRgn`，导致圆角边缘锯齿且丢失 Win11 原生柔和阴影。
- **升级方案**：首次异步取光标且无有效兜底坐标时，允许 `8–12 ms` 极短等待窗口（等 `OnCaretRectResolved` 到达后直接一步到位显示，超时再兜底）；Windows 11（Build ≥ 22000）优先启用 `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE, DWMWCP_ROUND)` 获原生抗锯齿圆角与立体投影。

## 四、维度 C 深度评估——易用性与全场景体验（Usability）

易用性决定普通用户“安装即好用、不用折腾配置文件也能打得顺畅”的留存率。走查 [settings_window.cpp](../platform/windows/src/settings_window.cpp)、[config_reader.h](../platform/windows/include/config_reader.h)、[fuzzy.rs](../engine/src/fuzzy.rs)、[shuangpin.rs](../engine/src/shuangpin.rs)：

### 4.1 【P0】模糊音“9 组捆绑默认全开”且无音节边界替换（产生非法垃圾音串）
- **代码实证**：
  1. **强买强卖式默认**：[config_reader.h#L116](../platform/windows/include/config_reader.h#L116) 默认 `fuzzy_enabled = true`，而 [fuzzy.rs#L15-L25](../engine/src/fuzzy.rs#L15-L25) 将 `z↔zh`、`c↔ch`、`s↔sh`、`an↔ang`、`en↔eng`、`in↔ing`、`n↔l`、`f↔h`、`r↔l` 全部 9 组写死在单一布尔开关下。这导致大量仅需 `z↔zh` 或完全标准发音的用户被迫承受 `f↔h`（发↔哈）、`n↔l`（你↔李）、`r↔l` 带来的候选污染。
  2. **无音节边界的子串暴力替换 Bug**：[fuzzy.rs#L48-L68](../engine/src/fuzzy.rs#L48-L68) 直接用 `input[pos..].find(from)` 做纯文本子串替换：
     - 输入 `"zhang"` 时，把 `"z"` 替成 `"zh"` 生成非法串 `"zhhang"`，把 `"an"` 替成 `"ang"` 生成 `"zhangg"`；
     - 输入 `"fan"` 时，把韵尾 `"n"` 当成声母替换生成 `"fal"`！大量无效字符串白白消耗词库查询和排序算力。
- **升级方案**：
  - 将默认策略调整为**总开关默认关闭**（或提供「仅平翘舌/前后鼻音」常用推荐预设），并在「设置 → 输入」拆分为 **9 组独立子开关**（`fuzzy_flags` 位掩码）；
  - 重写 `fuzzy_variants`：先借 `SyllableTrie` 切分为音节序列，**仅对声母前缀匹配 `z/zh, c/ch, s/sh, n/l, f/h, r/l`、仅对韵母后缀匹配 `an/ang, en/eng, in/ing, ian/iang, uan/uang`**，彻底消灭 `"zhhang"` / `"fal"` 等非法变体。

### 4.2 【P0】缺「竖排候选窗」布局与主流翻页键/习惯预设
- **代码实证**：
  1. [candidate_window.cpp](../platform/windows/src/candidate_window.cpp) 只支持单行横排与按 `↓` 展开的 5 列网格，**完全不支持竖排模式（Vertical Layout）**；习惯微软竖排、Rime 竖排或经常输入长句/英文单词混排的用户，在横排下极易被长候选挤出或截断。
  2. [config_reader.h#L88-L91](../platform/windows/include/config_reader.h#L88-L91) 默认把 `page_minus_equal`、`page_brackets`、`page_comma_period` 全设为 `false`（仅 `PgUp/PgDn` 可翻页）。全网 90% 以上中文桌面用户习惯按 `-`/`=` 翻页，首次使用泰深按 `=` 却打出一个 `=` 上屏，极易误以为“不支持翻页”。
- **升级方案**：
  - 实现真正的**竖排候选渲染模式**（支持每项独立占行、完整显示长句与 `comment` 注释）；
  - 将 `page_minus_equal`（主键盘 `-/=` 翻页）设为**出厂默认开启**；在「基础 / 按键」页顶部提供**「迁移预设」一键切换**（「微软拼音习惯」「搜狗拼音习惯」「Rime 极客习惯」）。

### 4.3 【P1】设置细节误导、功能发现性弱与「恢复默认」误伤用户列表
- **代码实证**：
  1. **双拼方案存在虚假兼容项**：[settings_window.cpp#L809](../platform/windows/src/settings_window.cpp#L809) 提示“紫光/加加按微软键位兼容，不建议选用”，[shuangpin.rs#L5](../engine/src/shuangpin.rs#L5) 实际直接复用了 `mspy` 表——对紫光双拼或拼音加加老用户造成误导。
  2. **「恢复默认」无确认静默清空应用规则**：[settings_window.cpp#L708-L711](../platform/windows/src/settings_window.cpp#L708-L711) 点击底部「恢复默认」直接执行 `m_cfg = ImeConfig()`，不仅重置参数，还会直接清空用户在「高级」里辛苦配置的游戏/终端 `app_*` 列表。
  3. **首次运行引导与特色模式提示缺失**：安装后无向导让用户选择「全拼/双拼」「横排/竖排」「翻页键」，输入 `v`/`u`/`c`/`R`/`U` 单字母进入特殊模式时，候选窗顶部无轻量模式提示标签。
- **升级方案**：补齐真实紫光/加加双拼映射表（仅各约 40 行映射数据）或明确下线；「恢复默认」拆为「恢复常规设置（保留应用规则）」或增加二次确认；补齐安装完成后的轻量 1 页「上手偏好设置卡片」及特殊模式微引导标签。

### 4.4 【P1】场景智能感知门槛高（手填 `.exe` 进程名对普通用户不友好）
- **代码实证**：当前要让终端、代码编辑器或特定游戏自动切换英文/禁用行内预编辑，用户必须自己打开任务管理器查 `.exe` 名再到「高级 → 应用级配置」手动键入（[settings_window.cpp#L935-L1029](../platform/windows/src/settings_window.cpp#L935-L1029)）。
- **升级方案**：配合 P1-1 的 `ITfInputScope` 自动免配识别密码框/URL/数字框；在「高级」页为「+ 添加程序」增加**「从当前已打开窗口中选择…」进程列表拾取器**，并维护一份可更新的常见游戏/终端出厂兼容默认规则。

### 4.5 【P2】用户词库管理与数据自主权（可视化、导入导出、一键清空）
- **代码实证**：[settings_window.cpp#L676-L677](../platform/windows/src/settings_window.cpp#L676-L677) 8 个导航页中无词库/个人数据管理页；语音页（[#L1159](../platform/windows/src/settings_window.cpp#L1159)）仍提示模型管理待上线且出错仅写日志无 UI 提示。
- **升级方案**：新增「词库与数据」设置页：显示系统/领域/用户词条数、支持搜索/删除已学用户词与置顶降权词、支持 TXT/TSV 词库导入导出备份、支持一键清空错误自学习历史；为语音启动失败补齐轻量 Toast/状态气泡提示。

## 五、维度 D 深度评估——全链路性能与资源治理（Performance）

v1 方案与 [HANDOFF-2026-11-22](handoff/HANDOFF-2026-11-22-dict-memory-and-latency.md) 仅度量了 Rust 引擎 CLI 进程的内存与函数耗时，**尚未覆盖真实的端到端交互路径（硬件按键 → TSF → IPC → 引擎 → Direct2D → TSF EditSession 上屏）**。本节给出全链路瓶颈分析与量化基线：

### 5.1 【P0】D2D 候选窗每键重复创建/销毁 `50–126` 个 `IDWriteTextLayout` COM 对象
- **代码实证**：在 [candidate_window.cpp#L125-L383](../platform/windows/src/candidate_window.cpp#L125-L383) 中，`UpdateState` 触发一次渲染时会发生：
  1. `PositionWindow` → `CalculateSize` 遍历全部 `N` 个候选 **2 遍**（#L197 算 `maxItemWidth` + #L212 算总宽），每条候选调用 `ItemWidthDip` → `LabelWidthDip` + `MeasureTextWidth`，即调用 `UIRenderer::MeasureText`（[ui_render.cpp#L272](../platform/windows/src/ui_render.cpp#L272) 创建并立即 `Release` `IDWriteTextLayout`）`2N` 次（带 `comment` 则 `3N` 次），合计 **`4N`–`6N`** 次；
  2. `UpdateWindow` → `Draw` 遍历候选 **2 遍**（#L305 再算一遍 `maxItemW` = `2N` 次 + #L325 逐条重算 `ItemWidthDip`/`LabelWidthDip`/`MeasureTextWidth` + `r.DrawText` 内部 D2D 再建 `IDWriteTextLayout`），合计 **`6N`–`8N`** 次；
  3. **总计**：默认 5 候选单键创建/销毁 **`~50` 个** `IDWriteTextLayout` COM 对象，9 候选 **`~91` 个**（有 `comment` 时达 **`~126` 个**）；且 `OnMouseMove`（#L386）每移动 1 像素就调用 `CandidateAt` 重新创建 **`2N`–`3N`** 个布局对象！
- **升级方案**：在 `CandidatePanel::SetData`（或字体/缩放变更）时**一次性构建布局缓存 `std::vector<CachedItem>`**（预存 `wordLayout` / `labelLayout` / `commentLayout` 与命中矩形 `D2D1_RECT_F`）；`CalculateSize` 直接汇总缓存宽度，`Draw` 直接调 `ID2D1RenderTarget::DrawTextLayout`，`CandidateAt` 纯内存矩形命中。预期将候选窗测量+渲染单帧耗时压至 **`< 0.2 ms`**，鼠标划过 CPU 接近 0%。

### 5.2 【P0】`bigram.db.bin` 零拷贝 mmap 收口（P6 内存收口：`39.8 MB` → `< 12 MB`）
- **代码实证**：虽然系统词库、领域词库、语言模型已完成 `TSDICT06`/`TSDOM003`/`TSLM0001` mmap，但 [dictionary/mod.rs#L6417-L6498](../engine/src/dictionary/mod.rs#L6417-L6498) 中的 `BIGRAM`（38.6 万条搭配）仍以 `TSBGRAM2` 格式在堆上全量 `bincode::deserialize` 为 `HashMap<String, Vec<(String, u32)>>`，占据当前 `39.8 MB` 私有内存的最大份额，并在 [ffi.rs#L295-L314](../engine/src/ffi.rs#L295-L314) 首键按键时新开后台线程执行 ~200ms 的密集堆分配与反序列化。
- **升级方案**：参照 [EVAL-20261122.md §1.2](modules/dict-memory/EVAL-20261122.md) 中 `4.2 MB` 扁平化测算，复用 `mapped.rs` 基础设施将 `bigram.db.bin` 升级为 **`TSBGRAM3` 只读 mmap 容器**（共享前词/后词池 + 有序索引二分）。落地后可实现：
  - 单进程私有内存 **`39.8 MB → < 12 MB`**；
  - 消除首键 `200 ms` 后台线程反序列化尖峰，改为 `< 1 ms` 零堆分配 mmap 映射。

### 5.3 【P0】消除 `ActivateEx` 宿主 UI 线程同步 SQLite/YAML 阻塞与清理托盘死代码
- **代码实证**：
  1. [tsf_module.cpp#L1274](../platform/windows/src/tsf_module.cpp#L1274) → [ffi.rs#L193-L214](../engine/src/ffi.rs#L193-L214) 在激活窗口的宿主 UI 线程连续 **3 次同步调用 `Connection::open` 打开 `user_dict.db`**（含两次 `write_back::flush(true)`）；
  2. [tsf_module.cpp#L1305](../platform/windows/src/tsf_module.cpp#L1305) 同步阻塞解析 2.1 MB、13.2 万行的 `radical_pinyin.dict.yaml`（[radical.rs#L34](../engine/src/radical.rs#L34)）；
  3. [tsf_module.cpp#L1508-L2160](../platform/windows/src/tsf_module.cpp#L1508-L2160) 仍残留约 400 行停用的托盘代码及空桩调用（[#L3018-L3020,L3260-L3262](../platform/windows/src/tsf_module.cpp#L3018-L3020)）。
- **升级方案**：随 V4 Step 4 把引擎迁入 `taishen_server.exe` 常驻；同时合并 `user_dict.db` 初始化为单连接单事务读取，将 `radical_pinyin` 改为编译期 `.bin` mmap 或 `u` 前缀懒加载，物理移除 `tsf_module.cpp` 全部托盘死代码。

### 5.4 【P1】长串尾延迟削峰与服务端空闲唤醒归零
- **代码实证**：
  1. `zhongguorenmin (limit=5)` 在 `lat_probe` 峰值仍为 `20.79 ms`（[HANDOFF-2026-11-22 §3](handoff/HANDOFF-2026-11-22-dict-memory-and-latency.md#L75)），其中 `zhongg` 阶段占 `15.6 ms`；叠加 V4 跨进程管道通信与 D2D 绘制后，端到端延迟接近 25–30 ms 边界。
  2. `taishen_server.cpp#L1508` 挂载了常驻 2 秒 `WM_TIMER`（`kTimerMaintenanceMs`），各连接线程内还有 `500 ms` 轮询检查 `shuttingDown`，在笔记本移动办公场景下会造成不必要的 CPU 唤醒。
- **升级方案**：
  - **引擎削峰**：对末尾处于非完整音节过渡态（如 `zhongg`）的输入，限制 `phrase_group_guess` 仅对已闭合音节前缀做容错迭代，使引擎单键 **P99 `< 5 ms`**；
  - **空闲 0 唤醒**：服务端迁入 IOCP 事件驱动后彻底移除 `500 ms` 轮询；维护定时器改为“仅当存在待写盘用户词队列或 `config.ini` 目录变更通知（`ReadDirectoryChangesW`）时触发”，静默打字间隔时 **CPU 唤醒 = 0**；
  - **IPC 管道序列化提速**：将当前手写文本 JSON（[render_ipc.h](../platform/windows/include/render_ipc.h)）逐步收口为定长二进制协议（或零拷贝栈缓冲编码），消除堆上字符串拼接与解析开销。

### 6.3 【P1】整句解码核心算法的三项结构性破局
针对 [DIAGNOSIS-20261121.md](modules/sentence-quality/DIAGNOSIS-20261121.md) 已证伪“单纯加口语词表或盲目调大 bigram 权重无效”的教训，提出三项结构性改造：
1. **消除 `LN_RAW_TOTAL = 17.944` 一元固定切词惩罚带来的“合成词压死高频单字连用”缺陷**：
   - **病灶**：[sentence.rs#L61](../engine/src/sentence.rs#L61) 对每个词块独立扣除 `-17.944`，导致两字拆开（如「刚+到」）扣两次共 `-35.888`，永远输给仅扣一次 `-17.944` 的生僻词「钢刀」。
   - **解法**：将切词转移评分改造为**条件二元语言模型概率**——当 `w1 -> w2` 命中 `TSLM` 二元边时，直接使用平滑二元条件对数概率 `ln P(w2 | w1)` 替代独立的 `-17.944` 一元先验回退，从数学上根除“宁出「钢刀」不出「刚到」”的结构偏向。
2. **打破束塌缩（Beam Collapse）与解决 16 组虚实词倒挂（「在/再」「此/词」「该/改」「见/键」）**：
   - **病灶**：前 9 个整句候选往往只在句尾换字，句首一旦错选高频虚词「在」，其余 8 个候选全军覆没。
   - **解法**：① 引入 **Diverse Beam Search / 同音高歧义对双轨保留策略**（在束剪枝 `prune_at` 时，对高冲突同音字保留不同首字分支，确保即使 Top-1 出了「在」，Top-2/3 必有「再」的整句路径）；② 推进 **3-gram 剪枝模型 + 10–30 MB 本地 INT8 轻量神经语言模型（Top-8 重排，3–8ms）** 彻底解决长距语境语义消歧。
3. **打通长串纯声母全简拼（`0/90` → `≥ 65%` Top-3）**：
   - **病灶**：[sentence.rs#L105,L116](../engine/src/sentence.rs#L105) 限制伪段最大长度 `4` 且固定惩罚 `4.0`，全声母长句在 `char_graph` 中无法跨段组合。
   - **解法**：针对 `!splits_clean` 的纯声母序列引入专门的 `short_index` / `common_short` 多字词图切分通道（结合首尾常用搭配打分），让 `wmyqcf`（我们一起吃饭）这类日常高频全简短句具备可用输出。

### 6.4 【P1】自学习收敛速度、配置连通与防误触污染治理
- **代码实证**：
  1. [ffi.rs#L214](../engine/src/ffi.rs#L214) 与 [lib.rs#L5880](../engine/src/lib.rs#L5880) 硬编码 `load_context_pairs(2, 8)`，导致 [tuning.rs#L31](../engine/src/tuning.rs#L31) 的 `learned_context_cap` 配置项实际在加载阶段不生效；
  2. 虽然 [dictionary/mod.rs#L2360](../engine/src/dictionary/mod.rs#L2360) 已有读音校验防错位写入，但用户词索引缺乏**时间衰减（Time Decay）**与**新自造词二次确认升权**机制——偶然在组词态或冷门位置点选一次的非预期词会直接以高权重留在首屏。
- **升级方案**：打通 `tuning().learned_context_cap` 全链路读取；引入基于 `last_used` 的半衰期衰减公式（如 30 天半衰期）与新词 `freq=1` 温启动保护（第 1 次选中不立即夺取精确高频词第 1 位，第 2 次起跃升首位）。

### 6.5 【P2】多模态与边缘场景输出质量（儿化、繁简、生僻字字体回退）
- **儿化音切分规则**：在 `pinyin/mod.rs` 与查询层支持常见儿化尾 `r`（如 `huar → hua'er 花儿`、`wanr → wan'er 玩儿`、`yidianr → yi'dian'er 一点儿`），消除儿化词依赖碰巧漏字纠错才能命中的脆弱状态（[CASE-AUDIT.md §5.2 L148](modules/exam/CASE-AUDIT.md#L126)）。

- **CJK 扩展区生僻字渲染防豆腐块**：在 [ui_render.cpp#L225-L229](../platform/windows/src/ui_render.cpp#L225-L229) 为 `IDWriteTextFormat` 挂载字体回退链（覆盖 CJK Ext-B–I，如 `SimSun-ExtB` / `Segoe UI Emoji`），防止拆字模式与生僻人名显示为 `□`。
