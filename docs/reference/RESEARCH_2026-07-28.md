## 一、核心参考项目

### 1.1 RIME（中州韻輸入法引擎）

| 维度 | 详情 |
|------|------|
| **仓库** | github.com/rime/librime |
| **Stars** | 4,500+ |
| **语言** | C++17（80.5%）+ C（15.1%） |
| **依赖** | Boost, LevelDB, marisa-trie, OpenCC, yaml-cpp |
| **许可证** | BSD-3-Clause |
| **活跃度** | 1,905 commits，最后更新 3 天前（2026-07-25），非常活跃 |
| **最新版本** | 1.17.0（2026-06-05） |

**架构亮点**：
- 引擎与前端分离。核心 librime 一个 C++ 库，各平台各自写前端：Weasel（Windows）、Squirrel（macOS）、ibus-rime（Linux）
- YAML Schema DSL — 输入方案用 YAML 描述，不改代码就能设计新输入法
- Spelling Algebra — 拼写变体机制，支持容错拼写、方言拼音
- 插件架构 — lua 脚本、语言模型（octagram）、预测（predict）、IPC（proto）
- marisa-trie 做词典索引，LevelDB 做持久化

**对我们的启示**：
- 引擎/前端分离模式已经被 RIME 验证——我们 Rust 引擎 + C++ TSF 前端的架构与之同构
- YAML 配置方案值得参考，但我们的完整分层配置（默认→安装→用户）更细腻
- LevelDB 在这里用于词库持久化，但 SQLite 更透明、工具链更成熟
- RIME 的依赖链很重（Boost + LevelDB + yaml-cpp + OpenCC），我们的 Rust 方案可以轻得多

### 1.2 PIME（Windows TSF 输入法框架）

| 维度 | 详情 |
|------|------|
| **仓库** | github.com/EasyIME/PIME |
| **Stars** | 1,500+ |
| **语言** | C++（TSF 核心）+ Python（后端）+ Node.js（部分后端）+ Rust（部分模块） |
| **许可证** | LGPL v2.1 |

**架构亮点**：
- LibIME 封装了 Windows TSF API，使其更易用
- PIMETextService 是 TSF Text Service 的标准骨架实现
- 通过 IPC 将 TSF 事件转发给 Python/Node.js 后端处理
- 同时编译 32 位和 64 位 DLL（`regsvr32` 注册 COM）
- 使用 CMake + Visual Studio 构建
- **正在引入 Rust 工具链**（i686-pc-windows-msvc target）

**对 Windows TSF 开发的启示**：
- TSF DLL 必须同时提供 x86 和 x64 版本
- COM 注册用 `regsvr32`，64 位系统需注册两个版本
- 需要放在 `Program Files` 下才能被 UWP 应用访问
- `ITfTextInputProcessorEx` 是核心接口，`ITfKeyEventSink` 接收按键
- ACL（访问控制列表）配置很重要——Windows 8+ 的 AppContainer 隔离

**对我们的启示**：
- PIME 的 TSF 骨架结构可以直接参考：`PIMETextService` → 我们的 `tsf_module.cpp`
- PIME 正在引入 Rust，验证了 "Rust + TSF" 方向的可行性
- 但我们不做 IPC 转发——直接 FFI 调用，省掉进程间通信的复杂性

## 二、技术方向调研

### 2.1 Rust 拼音生态

**结论：非常稀疏，没有成熟的拼音引擎 crate。**

搜索 crates.io 和 GitHub 发现：
- 有一些拼音转换库（汉字→拼音），但没有完整的拼音输入法引擎
- 没有现成的 Rust IME 框架或 TSF 封装

这意味着我们从零构建 Rust 引擎的方向是正确的——空白市场 + 技术差异化。已实现的 400+ 音节表和前缀索引是一个好的起点。

### 2.2 Skia 渲染引擎

| 维度 | 详情 |
|------|------|
| **维护者** | Google |
| **用途** | Chrome, Flutter, Android, Firefox |
| **Rust 绑定** | skia-safe crate（社区维护） |
| **优点** | 跨平台、高性能 2D、GPU 加速、文本渲染成熟 |
| **缺点** | 体积大（~15-30MB）、编译复杂、学习曲线陡、Rust 绑定不够成熟 |

**替代方案**：
- **tiny-skia**：纯 Rust 实现的 Skia 子集，零依赖，体积小，但功能有限
- **Direct2D（Windows 原生）**：Windows 自带，零额外依赖，但只支持 Windows
- **Cairo**：老牌跨平台 2D 库，Rust 绑定成熟，但性能不如 Skia

**建议**：第一期先用 Direct2D 快速验证 Windows 候选窗口。Skia 作为跨平台选项在 macOS 适配时再上。

### 2.3 Windows TSF 开发参考

微软官方 TSF 示例代码位置（PIME README 中引用）：
- [IME sample supporting Windows 8](http://code.msdn.microsoft.com/windowsdesktop/Input-Method-Editor-IME-b1610980)
- [Third-party IME guidelines](http://msdn.microsoft.com/en-us/library/windows/desktop/hh848069)
- [TSF Aware blog](http://blogs.msdn.com/b/tsfaware/)

PIME 的 `HACKING.txt` 和 `PIMETextService` 目录是 Windows TSF 实现的最佳实战参考。

## 四、差异化机会

| 机会点 | 说明 |
|--------|------|
| **Rust 引擎** | 相比 RIME 的 C++，内存安全、更现代的构建工具链、更好的 FFI 支持 |
| **体积优势** | Rust 静态链接 + SQLite 嵌入 → 无需 Boost/LevelDB/yaml-cpp 等重量级依赖 |
| **SQLite 词库** | 比 LevelDB 更熟悉的工具链，生态更好，直接可查询、可备份 |
| **分层配置** | 默认→安装→用户 三层比 RIME 的单一 YAML 更精细 |
| **Direct2D 渲染** | 第一期 Windows 原生渲染，零额外依赖；二期切 Skia 不伤架构 |
| **简单 FFI** | 直接 C ABI 调用，无 IPC 开销，比 PIME 的 Python 后端方案更轻 |

---

## 五、风险与注意事项

1. **Windows TSF 开发门槛高** — COM 编程 + 注册表 + 64/32 位双版本，是需要投入最多时间的部分
2. **PIME 使用 LGPL 许可证** — 可以参考其 TSF 架构思路（松耦合的模块划分），但代码不能直接复制
3. **Skia Rust 绑定不成熟** — skia-safe 维护频率低，第一期建议用 Direct2D 规避
4. **RIME 生态强大** — 雾凇拼音 2.9k star，社区活跃，作为竞品压力不小。差异化关键在 Rust + 体积 + 简单性
5. **微软 TSF 示例代码老旧** — MSDN 上的示例可能已不兼容最新 Windows SDK，建议以 PIME 为主要参考
