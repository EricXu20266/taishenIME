# 竞品选词逻辑对比 — 泰深 vs 雾凇（Rime-ice）

> 调研日期：2026-08-10
> 对比对象：泰深 V0.5.6（词库优先级分层 pick） vs 雾凇 rime-ice 2026-03-08（librime 引擎 + Lua filter 管道）
> 调研目的：项目接近尾声，全量测试 15702 用例命中 99.84%（常用词首选 1-9 全命中）后，对照竞品核心选词逻辑，确认无遗漏可借鉴项
> 数据来源：本地 `E:\AllinDeepSeek\rime-ice` 源码 + `docs/reference/candidate-ranking-logic.md` + `docs/reference/RESEARCH_2026-08-08-ime-benchmark.md`

## 一、两套选词逻辑的本质差异

### 泰深：词库优先级分层 pick（引擎逻辑层定优先级）

```
P1 用户词（热 > 温 > 过期衰减）
P2 常用词 common（人工 rank 行序）
P3 系统词 system（维基词频降序）
P4 领域词 domain（热度 > 词长 > 原序）
P5 联想兜底（纠错/模糊/简拼/组合）
```

核心原则：**低层级永不插队，不做跨层混排**。优先级写在引擎代码里，与词库数据无关。

### 雾凇：单一词池 + 显式权重混排（词库数据层定优先级）

```
所有词库 import 进同一个池（8105 > base > ext > tencent > others，重复词条最上面生效）
每词条带显式权重（如 阿巴桑 a ba sang 100）
引擎按 weight 降序输出；用户词典 userdb 动态调频覆盖
翻译器间用 initial_quality 分层（custom_phrase 99 > pinyin 1.2 > melt_eng 1.1 > cn_en 0.5）
Lua filter 管道微调最终顺序
```

核心原则：**词与词直接比权重**。优先级藏在词库数据的 weight 字段里，靠人工精调词频实现（雾凇 base.dict.yaml 55 万行，调频记录是主要维护内容）。

## 二、逐维度对比

| 维度 | 泰深 V0.5.6 | 雾凇 / librime | 评价 |
|------|------------|----------------|------|
| **排序模型** | 词库分层硬约束（P1→P5） | 单一词池按 weight 混排 | 泰深更结构化，雾凇更精细但靠人力 |
| **用户学习** | 热(7天) > 温 > 过期衰减回 common 后 | userdb 连续权重动态调频，无时间衰减 | 泰深有时间窗概念，雾凇累积更平滑 |
| **跨词库优先级** | 分层硬编码 | import_tables 顺序 + initial_quality | 殊途同归，泰深显式、雾凇隐式 |
| **简拼** | query_short 追加在整词候选后（P1→P4 分层） | speller algebra `abbrev` 生成变体，进同一词池参与排序 | 雾凇简拼变体与全拼同池比权重，泰深简拼默认排后 |
| **模糊音/纠错** | fuzzy_variants / correction 追加兜底 | `derive` 生成拼写变体，同池参与排序 | 同上——雾凇"变体进主流程"，泰深"变体做兜底" |
| **长词处理** | apply_word_len_match：N 音节→N 字词占前 4 位（分区） | long_word_filter：提升 count 个长词插入到 idx 位（默认 2 个→第 4/5 位） | 泰深分区更系统；雾凇"少量插入"更克制，不重排后续 |
| **置顶** | pin_map 内置硬编码（builtin_pins） | pin_cand_filter 配置驱动，**支持简拼自动展开**（'ni hao 你好' 自动生成 nih 置顶） | 雾凇配置化 + 简拼展开是亮点 |
| **英文候选** | 恒追加末尾（english_candidate_pos 之后） | reduce_english_filter 可配置降权位置 + 自定义单词表 | 泰深更简单，效果等价 |
| **删词/降频** | delete_candidate：从用户词库删除（Ctrl+Delete） | cold_word_drop：删词（Ctrl+D）+ **降频到第 4 位**（Ctrl+J）双档 | 雾凇有"降权中间档"，泰深只有删 |
| **上下文联想** | apply_context_boost：last_committed 关联词前置 | 默认无（可选 octagram 语法模型，max_sentences 默认 1） | 泰深领先 |
| **领域词** | P4 独立层 + 领域热度自适应（选词升温） | 无领域概念，全并入大词库 | 泰深领先 |
| **繁简** | 简繁分集双词库（繁体优先原生繁体） | 全简体词库 + opencc 输出转换 | 泰深更准（V0.5.6 已解决） |
| **纠错深度** | 规则表 + 智能键位纠错 + 错音提示 | derive 规则（约 40 条）+ corrector.lua 提示 | 持平，实现同源 |

## 三、雾凇值得借鉴的 3 点

### 1. 冷词"降频"中间档（P0，最有价值）

雾凇 `cold_word_drop` 提供两档用户干预：
- **删词**（Ctrl+D）：彻底移除
- **降频**（Ctrl+J）：把指定候选压到第 4 位，不删除

泰深只有 `delete_candidate`（删用户词）。用户真实诉求往往是"我不想让它排第一"，不是"我要删掉它"——删词是破坏性的，降频可逆。**建议补一个"降权候选"机制**：把候选压到本页末位（或第 5 位），记录到用户词库特殊标记，重查时生效。

### 2. 置顶配置支持简拼自动展开（P1）

雾凇 `pin_cand_filter` 写 `'ni hao  你好'` 会自动生成 `nihao` 和 `nih` 两个置顶键——输入简拼 `nih` 时「你好」也能置顶。泰深 pin_map 是内置硬编码，且未覆盖简拼。

**建议**：pin_map 从内置表改为配置文件驱动（如 common_dict.txt 同格式的 pin.txt），并支持"空格分隔自动展开简码"。泰深已有 P2 common 层 + query_short 简拼，展开逻辑可复用。

### 3. 长词"少量插入"替代"全量分区"（P1，可选）

雾凇 long_word_filter 默认只提升 2 个长词到第 4/5 位，**不重排第 1-3 位**。泰深 apply_word_len_match 把 N 字词全量提到前 4 位。

两者效果接近，但雾凇的克制版在"前 3 位已被短词占满"时更稳。泰深 V0.5.5 删过 apply_long_word_filter（方向反），当前词长分区已验证全量命中，**不建议回退**，仅记录雾凇作为对照方案。

## 四、雾凇的隐性成本（泰深已规避）

| 雾凇做法 | 隐性成本 | 泰深做法 |
|----------|---------|----------|
| 词频靠 55 万行词库人工精调 | 维护量巨大，调频记录是主要 changelog | 分层硬约束，常用词无需调频 |
| 领域词并入大词池 | 需要人工保证权重合理，否则被淹没 | P4 独立层 + 热度自适应 |
| 简繁靠 opencc 转换 | 转换错误（如"干/乾"）需打补丁 | 简繁分集双词库 |
| 变体进主流程（derive/abbrev） | 每键计算量大，候选噪声多 | 变体做兜底，主流程干净 |

---

## 五、结论

泰深的分层 pick 模型在**解决"常用词被领域词/长词淹没"**这一核心痛点上，比雾凇的"单池混排 + 人工调频"更彻底、更可维护——这也是雾凇词库需要长期人工精调才能达到的效果，泰深用引擎层规则做到了。

**真正值得补的只有 1 项（P0）**：雾凇"降频到第 4 位"的中间档用户干预，泰深目前只有"删除"这一破坏性操作。其余（置顶配置化、简拼展开、长词克制插入）均为可选项，不影响核心命中率。

**不建议借鉴**：雾凇的简拼/纠错变体进主流程（泰深兜底方案已够用且更干净）、opencc 简繁转换（泰深分集更准）、人工词频调优（泰深分层已免此负担）。
