# 引擎内存治理方案独立评估报告（2026-11-22）

> 评估背景：常驻内存实测 949 MB 私有字节（加载峰值 1,138 MB），目标降至 100–300 MB；不改查询语义（主用例 278/292、长句全拼 36/90、虚词简 31/90），`lat_probe` 的 `zhongguorenmin` 峰值不超过 97 ms。
> 关联设计稿：[SPEC-mmap-index.md](SPEC-mmap-index.md)

## 一、现状复核与四个关键发现

### 1. 现状验证

跑通 [mapped_check.rs](../../../engine/examples/mapped_check.rs) 一致性验证：

- 比对规模：`1,070,506` 个前缀（含 6 个不存在键，共 `1,070,512` 次查询）、`3,467,202` 条词条，**不一致为 0**。
- 性能表现：构建耗时 `1.20 s`，文件大小 `75 MB`，mmap 打开耗时 `6.32 ms`。
- 核对备注：`mapped_check.rs` 未做 `MAX_PREFIX_ENTRIES = 400` 截断（生产环境 `index` 实际为 `2,454,489` 条），且 8 分片各自建词池导致词串重复约 5.5 遍；同时当前 `mapped.rs` 仅覆盖 `index`，尚未覆盖其余 5 张系统索引与领域索引。

### 3. 决定方案优劣的架构前提（进程内 TSF DLL + 32 位宿主）

核查 [CMakeLists.txt](../../../platform/windows/CMakeLists.txt) 与 [package.ps1](../../../package.ps1) 确认：

- `taishen_server.exe` 目前仅负责渲染，不含引擎；[taishen_engine](../../../engine/Cargo.toml) 静态链接在 64 位 `taishen_ime.dll` 与 **32 位 `taishen_ime_x86.dll`** 中，直接注入每个宿主进程。
- **多进程乘数**：堆内存方案在 N 个活跃应用（浏览器 / 聊天软件 / 编辑器 / 终端）下会消耗 **N × 单进程私有内存**；而 Windows 只读文件 `mmap`（`PAGE_READONLY`）由操作系统**跨进程 100% 共享同一份物理页**，开 10 个进程仍只占 1 份物理 RAM。
- **32 位宿主红线**：32 位进程用户态地址空间仅 2 GB，当前 949 MB 私有堆（峰值 1,138 MB）极易 OOM；即便改用 mmap，映射文件总大小也应控制在 **≤ 100–130 MB**，防止 32 位虚拟地址空间碎片化失败。

### 4. 对现有设计稿与 `mapped.rs` 的独立审计（6 处需先修正的隐患）

审阅 [SPEC-mmap-index.md](SPEC-mmap-index.md) 与 [mapped.rs](../../../engine/src/dictionary/mapped.rs) 后，发现若按现稿直接接入，会在 P1/P2 和线上升级时遇到 6 个问题：

1. **8 分片哈希路由在 mmap 下属于负优化**：`ShardedMap` 原只为并行反序列化 bincode；mmap 无反序列化，哈希分片反而带来三害：① `word_pool` 被重复存 8 份（多占 ~14–17 MB）；② **破坏全局字典序，`range()` 无法单段扫描**；③ 使用了 `std::collections::hash_map::DefaultHasher`（Rust 不保证跨版本稳定，且 32/64 位 `usize` 截断存在隐患）。应改为**单表全局有序 + 首/双字母目录（O(1) 缩小二分区间，无需哈希，天然支持 `range()`，全库仅 1 份共享 `word_pool`）**。
2. **`merge_domains` 运行期写 `trad_index`**：[mod.rs:2023-2031](../../../engine/src/dictionary/mod.rs#L2023-L2031) 在领域加载后会向 `self.trad_index` 插入领域繁体词。若 `trad_index` 切只读 mmap，必须拆成系统繁体与领域繁体双源查询，不能原地修改。
3. **Windows 覆盖安装锁文件风险（高危）**：[install.nsi:156-163](../../../install/install.nsi#L156-L163) 与 [install.ps1:121-129](../../../install/install.ps1#L121-L129) 对 DLL 做了「改名 `.old.<ts>` + `Delete /REBOOTOK`」，但对 `.bin` 仍是直接覆盖。一旦宿主进程持有 mmap，覆盖安装会因共享冲突失败；且若允许 `FILE_SHARE_WRITE` 外部原地修改已映射文件，会直接触发 UB / `STATUS_IN_PAGE_ERROR`。必须用 `FILE_SHARE_READ | FILE_SHARE_DELETE` 打开，安装脚本同步改名策略，运行时写缓存走「写临时文件 → 原子 rename」。
4. **调用点实际很收敛**：全库扫描 `self.index` 在生产代码中仅有 **4 处查询调用**（全部在 [query_with_split](../../../engine/src/dictionary/mod.rs#L3030) 与 [query_with_split_meta](../../../engine/src/dictionary/mod.rs#L3163) 中，且每函数内对同一 `key` 查了两次，可合并为 1 次）。
5. **双轨代码风险**：`from_builtin`、`from_sqlite` 与单测仍需内存构建。应抽象 `enum Backing { Mmap(Mmap), Owned(Vec<u8>) }` 统一只读视图，避免 `HashMap` 与 `MappedIndex` 两套查询实现长期并行产生语义漂移。
6. **`mapped.rs` 热路径细节**：目前每次 `get()` 都重算分片内偏移且每轮二分都调用 `from_utf8`（ASCII 键可直接 `&[u8]` 比较，偏移应在 `open()` 预解析）；且 `Entry` 注释写 16B 实为 12B，共享词池后可用 `word_id(24b) + py_len(8b) + freq(32b)` 压缩为无损 **8B**（支持 1,677 万词 / 255 拼音长 / 42 亿词频，实测当前最大值 37.1 万词 / 34 长度 / 11,651 词频）。

| 方案 | 单进程稳态收益（基线 949 MB 私有 / 923 MB WS） | 多进程（5 宿主）总物理内存 | 磁盘 / 映射 VA 体积 | 风险 | 工程量 | 对现有体验与约束的影响 |
|---|---|---|---|---|---|---|
| **a. 改进版 mmap 零拷贝**（统一词池 + 单表有序 + 全索引覆盖） | **P1**：私有 -340 MB → ~609 MB<br>**P1–P4**：私有 **-800 MB → ~150 MB**，WS ~190–230 MB<br>**P1–P5（含 LM+bigram）**：私有 **-925 MB → ~25 MB**，WS **~80–130 MB** | P1–P4：~800 MB<br>**P1–P5：~200–250 MB**（100% 物理页共享） | 系统 69 MB + 领域 28 MB = **97 MB**（含 LM+bigram 约 **127 MB**） | **低–中**（Windows 升级锁文件需同步改安装链） | P1：1.5–2 天<br>P1–P4：4–5 天<br>P1–P5：5.5–6.5 天 | **零退化**；逐条 100% 一致（含同频 tie-break）；加载 ~500 ms → <30 ms |
| **b. 砍掉前缀索引，改音节组合** | 仅砍 `index`/`dom_index`/`trad` 约 **-470 MB**，余下索引+LM+bigram 仍占 **~480 MB**（达不到 100–300 MB，仍需叠加 d/a） | 5 × ~480 MB ≈ **2.4 GB** | ~100 MB | **极高**（直接违反「不改查询语义」硬约束） | 5–10 天+（重做排序与补全链路） | **严重负面**：丢失半音节补全（`niha→你好`、`dianjishiy→点击使用`），主用例集大面积退化 |

### 关于第六种方案（方案 f）的实证依据

对 `system_dict.db` 全部 `1,070,506` 个前缀的扇出度（命中多少个不同完整拼音）做全量统计：

| 前缀命中完整拼音数 | 涉及前缀 key 数 | 占总前缀比例 | 截断后 entry 数 | 含义 |
|---|---:|---:|---:|---|
| 恰好 `= 1` | `900,094` | **84.08%** | `928,522` | 84% 的前缀只对应 1 个完整拼音，在 `full_index` 中早已排好序 |
| `≤ 8` | `1,044,720` | **97.59%** | `1,413,006` | 绝大多数前缀在 `full_index` 顺扫 ≤8 项即可还原 |
| `≤ 32` | `1,064,320` | **99.42%** | `1,788,961` | 最多顺扫 32 个相邻有序键（~1–3 µs） |
| **`> 32`（高扇出）** | **仅 `6,186`** | **0.58%** | `665,576` | **仅需预存这 6,186 个高扇出前缀（8B Entry = 5.3 MB）** |

同理，`trad_index` 高扇出 `>32` 仅 `333` 个 key（`0.9 MB`），`dom_index` 仅 `3,540` 个 key（`~3 MB`）。无需砍掉任何前缀补全能力，仅靠「有序 `full_index` + 0.58% 高扇出预计算表」即可消除 99.4% 的冗余前缀键。

- *唯一需注意的细节*：`system_dict.db` 有 `335,389` 行拼音带 `'`，旧构建 `ORDER BY pinyin` 按带 `'` 排序（`'` < `a`），与 `full_index` 去 `'` 排序在**极少数跨拼音完全同频词**上可能存在 tie-break 次序差；因此方案 f 必须在全量用例上核验，或在构建端保持一致顺序。

### 补充架构视角（第七种：引擎迁入 `taishen_server.exe` 进程外单例）

若未来将引擎从 DLL 迁入现有的 `taishen_server.exe`，可彻底消除多进程重复加载与 32 位地址空间问题，但工程量极大（81 个 FFI 改 IPC + 崩溃恢复 + AppContainer 管道）且**不降低单实例 949 MB 占用**。本阶段不建议动进程架构；**mmap 是当前架构下投入产出比最高、且未来即便迁进程外仍 100% 复用的正交方案**。

## 三、推荐方案与分阶段路线

### 推荐选择：**改进版方案 a（全索引扁平 mmap，含 P5 覆盖 LM + bigram）为主干；方案 f（高扇出稀疏前缀）作为 P2/P4 可选瘦身项**

**核心理由**：

1. **唯有 mmap 同时击中三大痛点**：单进程 949 MB 私有内存 → **~25 MB（P1–P5）**、多进程 N× 翻倍 → **100% 共享物理页**、加载峰值 1,138 MB / 500 ms → **~130 MB / <30 ms**。相比之下，方案 b/c 违反语义硬约束，方案 d 无法跨进程共享，方案 e 有排序与尾延迟隐患。
2. **必须先修掉设计稿的 6 处隐患再定格式**：一次把格式定对（**去掉 8 分片与 `DefaultHasher`**，改为单表有序 + 双字符目录 + 共享词池 + 8B 无损 Entry + `Backing::{Mmap, Owned}` 统一读取端 + Windows 升级改名锁保护），避免 P1 落地后 P2 做 `range()` 时二次破格式。
3. **为什么要把 P5（LM + bigram）纳入规划**：实测 LM（78.8 MB）+ bigram（~52.8 MB）占 **~132 MB 纯私有内存**；若只做 P1–P4，5 进程下这两项仍占 ~660 MB 私有内存。一并扁平化/mmap 后，单进程 Working Set 可稳在 **80–130 MB**，私有提交仅 **~25 MB**。
4. **为什么先以改进版 a 保底、将方案 f 设为可选项**：改进版 a（~97 MB 系统+领域，含 P5 共 ~127 MB）已经完全满足 100–300 MB 内存目标与 32 位 VA 安全，且保证 **100% 逐条零偏差（含同频 tie-break）**；若希望安装包再瘦 ~42 MB 与 32 位 VA 压到 ~85 MB，可在 P2 `full_index` 落盘后叠加方案 f。

### 推荐实施节奏（每阶段独立可停、逐段回归）

| **基线固化** | 留存 `lat_probe`、`exam`、`tmp/lb-*.tsv`、内存时序基线 | 949 MB | 923 MB | 0.2 天 |

## 四、其他待处理项的优先级建议

1. **长输入延迟（`zhongg` 35 ms / `zhongguorenmin` 97 ms）**：**排在内存治理 P1–P4 之后**。当前 949 MB/进程（多进程数 GB + 32 位 OOM 风险）优先级更高；内存达标后直接上 `samply` / WPR+WPA 采样一次定位 95% 热点，半天到一天可精准收口。
2. **已有 5 个 commit 尚未部署**：建议等本轮内存治理（至少 P1–P4）落地并全量通过 404 单测 + `exam` + 三组长句后统一打包部署；若需先在日常使用中验证整句准确率提升，也可先基于现状部署一版，再切入内存改造。

## 五、待确认决策（确认后留基线并开工）

1. **路线确认**：是否采用 **改进版方案 a（去掉 8 分片 + 单表有序 + 共享词池 + 8B Entry + 安装锁保护）**？

## 六、评审定版结论（2026-11-22）

经交叉核实：LM 实测占用约 `70–79 MB`（为第三大内存大户）、`index` 生产查询点仅 `4` 处（含 `query_with_split` 与 `query_with_split_meta`）、`index` 截断后为 `245.4` 万条、`8` 分片哈希对 mmap 为负优化、Windows 覆盖安装存在 mmap 锁文件风险、且 `taishen_ime_x86.dll` 受 32 位宿主 2 GB 虚拟地址空间约束。最终定版路线如下：

1. **主干路线**：采纳**改进版方案 a**（单表全局有序 + 首字节目录 + 共享词池 + 8B 无损 Entry + `Backing::{Mmap, Owned}` 统一只读视图）。
2. **P1 硬性同步闭环**：**Windows 安装锁保护与原子写盘**同步进 P1（读取端 `FILE_SHARE_READ | FILE_SHARE_DELETE` 禁止原地写；运行时写缓存走写临时文件 + 原子 rename；`install.nsi` / `install.ps1` / `install_latest.ps1` 同步 `.bin` 改名替换策略）。
3. **分阶段节奏**：
   - `P1`：`Dictionary.index` 切入新容器 + 安装锁保护；
   - `P2`：`full_index` / `suffix_index` 切入同一 mmap 容器（`scheme f` 不进主线，P2 时仅补跑 1000 次顺扫微基准再判断）；
   - `P3`：`short` / `short_full` / `trad`（`trad` 拆系统与领域双源）；
   - `P4`：`domains` 五张索引全切统一 mmap 容器 —— **到此私有内存预期 ~150 MB、Working Set ~190–230 MB 达标后停下复盘**。
4. **P5（降到最后，P1–P4 实测达标后再评估）**：`lm.rs` 涉及多音字 `WordIds` 与准确率核心路径（+13.3 点），不与词库改造捆绑；后续如继续压缩，可拆分为低风险 `P5a`（`bigram` mmap）与高敏感 `P5b`（`LM`）。
