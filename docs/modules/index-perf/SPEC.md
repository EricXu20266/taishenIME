# 索引加载性能（V0.9）— SPEC

> 状态：设计完成待实施　创建：2026-10-27　Root：#1 #11

## 一、需求

缩短输入法激活后到真实词库可用（`DICT_READY`）的时间，改善切换输入法后立刻打字只有内置 33 条常用词可用的体感。

验收标准：release 构建下，`engine_init` → `dict_ready` ≤ 400ms（本机 P50），冷启动（杀软扫描 + 磁盘冷缓存）≤ 800ms。

## 三、瓶颈判断

反序列化是绝对瓶颈，I/O 不是。170 MB 对应约 890-1000ms，折算约 180 MB/s，符合 bincode 逐条分配 `String` + `HashMap` 插入的开销特征。

`index` 占 97 MB / 170 MB（57%）。它的膨胀来自两处结构冗余：同一词条会在每个拼音前缀下各存一份（`z`、`zh`、`zho`…… 各一条），且每条词条都持有独立的 `String` 副本。

## 四、方案对比

### 方案 A：分片并行反序列化（推荐先做）

把大索引按 key 的 hash 分成 N 个分片，序列化为 N 个独立段；加载时 N 个线程并行 bincode 反序列化，最后组装成分片数组。

- 预期收益：4 核下 890ms → 250-350ms
- 改动面：新增 `ShardedMap<V>` 包装类型（提供 `get` / `insert` / `entry` / `iter` / `len` / `values` 等现有用法），`index` 等字段改为该类型；.bin 增加格式版本头与段表
- 风险：内存峰值上升（多线程同时分配）；需保证分片规则与查询一致；旧 .bin 需自动重建
- 不动查询语义，是三条路线里唯一不触碰排序与匹配逻辑的

### 方案 B：字符串池化紧凑格式

序列化时把所有词条写入统一字符串池，索引条目只存池内偏移。体积预计从 170 MB 降到 50 MB 左右，反序列化减少约 200 万次 `String` 分配。

- 预期收益：反序列化 890ms → 300-400ms；磁盘读取 61ms → 约 20ms；杀软扫描量下降 3 倍
- 改动面：`Dictionary` 增加池字段，所有返回词的地方改为从池取；序列化格式 v2
- 风险：触及查询返回路径，回归面比方案 A 大

### 方案 C：mmap 零拷贝

改为 mmap + 有序数组 + 二分查找（参考青简 `.qj` 分节容器的思路，不复制其代码，注意对方是 GPL）。

- 预期收益：启动 < 100ms，内存按需分页
- 改动面：重写全部 query 系列函数的存储访问方式
- 风险最高，工期 1-2 周，不建议在当前阶段直接上

### 推荐路线

先做 A（1-2 天），拿到 300ms 级别的收益后再评估是否值得做 B。C 只在 A+B 仍不达标时考虑。

## 五、实施计划

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| 1 | .bin 格式加版本头（magic + version + 分片数），旧文件自动判失效并重建 | 用旧 .bin 启动应打印重建日志并生成 v2 文件 |
| 2 | 引入 `ShardedMap` 分片容器，先只包装 `index` | 单元测试：get/insert/iter/len 与原 HashMap 行为一致 |
| 3 | `build_index` 写出分片段；`from_bin` 多线程并行读取 | bench 打印各分片耗时 |
| 4 | 领域 .bin 同步改分片（165 MB 同样受益） | 领域词库加载日志分段耗时下降 |
| 5 | 回归：候选查询、排序、组词、简拼、后缀匹配、繁体 | cargo test 全绿 + first_char_verify 抽样 |

## 六、兼容与回滚

- `.bin` 带版本头：读到 v1 文件视为缓存失效，回退 SQLite 重建并写出 v2，不阻塞启动
- 分片数按 CPU 核数取（`available_parallelism`，上限 8），写死在文件头，读取端以文件头为准
- 回滚方式：删除 .bin 即回退到 SQLite 全量加载路径（现有逻辑不变）

## 七、不在本次范围

- 候选排序算法、词库内容、FFI 契约
- 领域词库 SQLite 构建耗时（构建期问题，非加载期）
- 内存占用优化（若实测峰值超过 1.5 GB 再单独立项）
