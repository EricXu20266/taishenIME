# 候选体系总设计（Candidate Ranking）

> 模块：engine 核心（Rust）
> 状态：现行实现（2026-11-17 校准）
> 覆盖：数据分层、字数分层、候选生成、排序算法、学习、搭配证据、诊断工具
> 关联：[business-flow.md](../../business-flow.md)（流水线全表）、[ARCHITECT.md](../../ARCHITECT.md)

本文件是**候选体系的唯一总纲**。各模块 SPEC（common-dict / user-dict / context-assoc / sort-mode / sentence-decode）只描述局部实现细节，冲突时以本文件为准。

---

## 一、设计目标与非目标

**目标**

1. **可解释**：任何一条候选为什么排在这个位置，都能说出是哪一维决定的。
2. **可回退**：每一维都是独立分区/排序，关掉一维不影响其他维（`context_enabled` / `sort_mode` / `phrase_enabled` 等开关）。
3. **冷启动可用**：出厂即有排序依据（常用词表 + 词频 + 搭配档位），不依赖用户积累。
4. **学习有效**：用户选过的词必须真的提前，而不是"写进库但排序不看"。

**非目标**

- 不做端到端神经网络打分（离线模型体积与首次加载延迟不可接受）。
- 不做云端候选。
- 不追求"每一条都最优"，追求"常用输入不出现明显错误排序"。

## 二、数据分层

### 2.1 五层取词（P1 → P5）

`dictionary::query` 内部按层取词，层内的相对顺序由各层自带的排序依据决定，**跨层顺序由 P 编号决定**。

| 层 | 数据源 | 规模 | 层内排序依据 | 说明 |
|----|--------|------|-------------|------|
| P1 | 用户词库 `user_dict.db` | 个人积累 | 热度（热 > 温 > 其他）→ 词频 | 见第六章 |
| P2 | 常用词表 `common.db` | 2732 条 | **行序**（人工优先级） | 独立于系统词库，命中即出候选 |
| P3 | 系统词库 `system_dict.db` | 37.3 万 | 词频降序 | 主体覆盖 |
| P4 | 领域词库 `domains.db` | 16.3 万 | 领域热度 → 词长 → 原序 | 命中领域词加权重 |
| P5 | 联想兜底 | 按需计算 | 见 4.2 | 纠错 / 模糊 / 简拼 / 组合 / 拆组 |

**关键约定**

- P2 的准入不依赖 P3：常用词表里的词即使系统词库没有，也能出候选。
- P5 只在候选不足一页或输入质量差时触发，避免噪声挤占首屏。
- 分层顺序在**取词阶段**确定，后续排序阶段可以跨层重排（例如 P2 的词被 `user_rank` 顶到前面）。

### 2.2 三类外部证据（不进候选，只影响顺序）

| 证据 | 数据源 | 用法 |
|------|--------|------|
| 常用词行序 | `common.db` 的 rank 列 | 多字词的 `common_rank` 维（0 = 在表内） |
| 搭配档位 | `context_prior` 表（40 万对，1-6 档） | 前文参与排序，见第七章 |
| 热度 | 用户词 `frequency` + `last_used` | 热/温/过期分档，见第六章 |

## 三、字数分层与词长策略

### 3.1 输入维度 N

排序不需要知道"用户想要几字词"，而是从**输入串**推算目标词长 N：

| 输入形态 | N 的推算 | 例 |
|---------|---------|-----|
| 完整拼音 | 全部可行切分的音节数集合 `counts` | `houxuan` → {2, 3} |
| 混合简拼 | 声母段 + 拼音段合计 | `zhyang` → 2（zh + yang） |
| 纯声母简拼 | 声母个数（≥2 才触发） | `nh` → 2 |
| 不可解析（英文/单字母） | 不干预 | `hello` |

**为什么用集合而不是单个数字**：`yuan` 既是 1 音节（元）也是 2 音节（预案），只认最长切分会把「预案」判成超长词压后。

### 3.2 字数分档的处理差异

| 字数 | 排序定位 | 特殊处理 |
|------|---------|---------|
| 1 字 | `group 0`（若 N=1） | 不参与常用词加权（单字保持词库词频序）；`user_rank` 仍生效 |
| 2 字 | `group 0`（若 N=2） | 主战场：常用词行序 + 搭配 + 用户学习三维竞争 |
| 3 字 | `group 0`（若 N=3） | 同上；整句解码可能产出 3 字组合，靠 `combo_like` 维压制 |
| 4-6 字 | 仅当 N 匹配时进 `group 0`，否则 `group 2`（长词） | 长词不抢首位；隔音歧义词（西安/提案）另有提升规则 |
| 短句 >10 字 | 在候选阶段被过滤 | 仅用户短语与整句解码结果豁免 |

**上限**：`MAX_CAND_WORD_LEN = 10`。普通词条超过 10 字不进候选（防候选窗溢出）；用户自定义短语与整句解码结果不受限。

### 3.3 候选预算

- 每页 `page_size` 默认 **5**（用户可配），最多 `max_pages = 8` 页 → 单次最多 40 条。
- 排序前先截断到 `RANKING_CANDIDATE_BUDGET = 4096`，避免长候选列表下排序成本失控。
- 截断后再 `truncate(page_size * max_pages)` 落最终列表。

## 四、候选生成

### 4.1 主查询链

完整流水线共 25 步，全表见 [business-flow.md](../../business-flow.md#核心数据流)。核心链路：

```
按键 → process_key（拼音累积 / 组词推进）
     → query_all
         ├ 特殊模式分派（符号 v / 计算器 c / 数字大写 R / Unicode U / 拆字 uR / 双拼 / 组词）
         ├ 日期时间简码
         ├ dictionary::query（P1→P5 分层取词）
         ├ 补充来源（见 4.2）
         ├ 排序链（见第五章）
         └ 截断 → publish → 平台层渲染
```

### 4.2 补充来源与触发条件

| 来源 | 触发条件 | 标注 |
|------|---------|------|
| 简拼 / 混合简拼 / 缩写+全拼 | 输入非完整拼音，或候选未满 | `Combo` |
| 模糊音变体 | 仅完整拼音 | `Fuzzy` |
| 邻键纠错 / 删除变体 | 仅完整拼音，候选不足 | `Correction` |
| 插入变体（漏打字母） | 输入不像话且前 3 位无常用词 | `Correction` |
| 错音提示 | 仅完整拼音，候选不足一页 | `Dictionary` |
| 逐音节组合 | 仅非完整拼音 | `Combo` |
| 锚定拆组 | 候选不足一页，或零命中且前 6 位无常用词 | `Combo` |
| 整句解码 | 纯小写、≥3 音节、≥8 字符、非英文词 | `Sentence` |
| 英文混输 | 恒在中文之后 | `English` |
| Emoji | 命中映射，最多 5 条 | `Emoji` |
| 用户短语 | 编码精确命中 | `Phrase` |
| 前缀补全 | 输入停在完整音节边界、精确段未命中所属词，候选拼音只多一个音节 | `Completion` |
| 日期/时间 | 简码或自然语言触发 | `Datetime` |

**拆组与联想的顺序（2026-11-18）**：两者都标 `Source::Combo`，主排序链视为平手，
**入列顺序就是最终顺序**。锚定拆组（以词库真实词组为锚）必须先于音节联想
（`query_combo`）入列——实测 `heshenm` 的联想产出「和圣玛」抢走首位，
拆组出的「和什么」被 append 到第 12 位，用户完全看不到。

**来源标注的用途**（`Source` 枚举）：决定英文区边界、是否参与置顶/降权/学习、排序最后一维的信任度。**每条候选必须带来源，无来源的候选不允许进入排序链。**

## 五、排序算法（核心）

### 5.1 阶段顺序及理由

排序是**多阶段串行**，每个阶段只做一件事。顺序不可随意调换，每一处都有对应的事故记录：

| # | 阶段 | 作用 | 为什么必须在这个位置 |
|---|------|------|---------------------|
| 1 | `apply_sentence_candidates` | 整句解码结果并入候选 | **必须在所有排序之前**。曾放在最后无条件插首位，绕过了整条排序链——`youxianji` 被解成「有县级 / 有限及 / 有限即」三条非词组合抢到前三，词库首位的「优先级」掉到第 4 位 |
| 2 | `apply_context_boost` | 前文搭配加权前移 | 搭配是"当前语境最相关"，应优先于词长分区 |
| 3 | `apply_word_len_match` | 词长分区 + 五维排序键 | 主排序。所有来源在此统一竞争 |
| 4 | `apply_ambiguous_split_boost` | 隔音歧义词提升 | 必须在词长分区之后——它要绕过分区把 `xian` 这类键的多音节词提到第 4 位 |
| 5 | `apply_pin_boost` | 用户置顶 | 置顶优先级高于分区，必须在分区之后 |
| 6 | 繁转去重 | 转繁后同文本只留原生繁体 | 去重前必须已完成排序，否则删错副本 |
| 7 | `apply_sort_mode` | 用户选择的单字/长词优先 | 用户显式配置，覆盖分区结果 |
| 8 | `apply_demote` | 降权词压出前 2 屏 | **必须最后**。曾放在 `sort_mode` 之前，单字优先会把降权词重新提回首屏 |
| 9 | Emoji 插入 | 插在英文区之前 | 英文区边界由来源表决定，必须已知 |
| 10 | 长句过滤 | >10 字词条剔除 | 必须在英文兜底之后，否则长串逃过过滤 |
| 11 | 单字母单字优先 | 单字母输入时单字排前 | 只对 1 字节输入生效，早做会被后续阶段打乱 |
| 12 | 预算截断 | `page_size × max_pages` | 最后一步 |

**补全位配额（2026-11-18）**：`apply_completion_boost` 的补全位数按窗口宽度动态分配，
不写死。单音节完整输入（`you` / `shi`）用户要的是单字，精确位停在「常用单字段后一格」
（`(common_run + 1).max(3).min(base)`，`base = page_size - 1`）；多音节按
`page_size / 3` 分配（上限 4）。

背景：写死 `COMPLETION_SLOTS = 4` 时，5 条窗只剩 `5-4=1` 个精确位，`you` 变成
「有 | 有的 有个 优酷 优化」——单字（又/由/右）整片挤出首屏；9 条窗下不可见，
所以只有窄窗用户（`candidate_count=5`）能复现。

### 5.2 排序键定义（`apply_word_len_match` 内）**五维字典序**，逐维比较，前一维相同才看后一维：

```
(group, exact_len_rank, user_rank, common_rank, combo_like)
```

| 维 | 取值 | 语义 | 典型冲突解决 |
|----|------|------|-------------|
| `group` | 0 / 1 / 2 / 3 | 0 = 字数 == N（匹配）；1 = `Completion`（音节边界补全）；2 = 字数 < N（偏短）；3 = 字数 > N（偏长） | 输入 `zhongguo`，3 字的「中国共产党」进 group 3，不抢首位 |
| `exact_len_rank` | 0 / 1 | 0 = 字数命中**首选切分**（最短完整切分）；1 = 命中其他切分 | `houxuan` 同时切 2/3 音节时，3 字的「候选窗」不得压 2 字的「候选」 |
| `user_rank` | 0 / 1 | 0 = 用户学过；1 = 未学过 | 学过「种果」后，它压过常用词表里的「中国」 |
| `common_rank` | 0 / 1 | 多字：0 = 在常用词表内；单字恒 0（保持词库词频序） | 单字不参与常用词加权，避免 `shua` 把「帅」提到「刷」前 |
| `combo_like` | 0 / 1 | 1 = 来源是 `Sentence` / `Combo`（拼出来的串） | `youxianji` 的「有县级」让位于词库真实词条「优先级」 |

**单字的特殊规则**：`common_rank` 对单字恒为 0。原因是单字音节内的高频字集中，若让常用词表对单字绝对优先，会把词库里更高频的单字挤掉（实测 `shua` 下「帅/率/算」会跑到「刷」前面）。单字的排序依据是**词库词频序 + `user_rank`**。

**纠错来源的额外规则**：完整拼音输入且候选里已有常用词时，`Correction` 来源整体退到 group 2。避免"另一条拼音猜出来的词"借词长对齐插到精确命中之前。

### 5.3 分区内保持稳定

所有分区都用稳定排序：**同分区内不改相对顺序**，相对顺序来自第 4 章的取词顺序（P1→P5）与各层内部排序。这样"某维没命中"时不会引入随机性。

## 六、学习体系

### 6.1 学什么 / 不学什么

**学习时机**：只在用户**主动选词**（`select_candidate`）时发生，浏览候选不学习。

| 类别 | 是否学习 | 原因 |
|------|---------|------|
| 普通中文词 + 完整拼音 | ✅ | 标准路径：`(拼音, 词)` 频率 +1 |
| 词库查不到的自造词 + 非完整输入 | ✅ | 用输入键当唯一读音 |
| 英文 / 短语 / 符号 / 计算器 / 日期 / 拆字 / 错音 | ❌ | 不是"这个词读这个音"的事实 |
| 整句解码结果（`Sentence`） | ❌ | 十几个字的整句写进用户库只会污染候选 |
| 纠错 / 模糊音结果（`Correction` / `Fuzzy`） | ❌ | 用户选的是一次猜测，不等于认定读音；学习会让误触变永久首选 |
| 打一半的拼音（`shuruf`）/ 简拼（`srf`） | ❌ | 不是可独立成立的读音，学进去同一词会攒出十几种别名 |
| 双拼奇数键末尾 | ❌ | 半个音节没进查询，学习键必然不完整 |

**读音一致性硬校验（2026-11-18）**：`learn_user_word` 是唯一落库入口，入库前必须通过
`pinyin_matches_word`：

1. 该读音的完整索引里确实有这个词 → 放行（多音字靠这条，不做单一读音裁决）；
2. 四层词库都查不到该词（自造词）→ 放行，输入键即它的唯一读音；
3. 有规范读音但不一致 → **拒绝**。

背景：候选索引错位 / 误触会写出 `l→你`、`li→你`、`ni→了` 这类记录。它们满足热词
条件（≥2 次、7 天内），入库后长期压过系统词频——实测用户库攒到 `l→你` 43 次时，
打 `l` 首位就是「你」，排序链怎么调都救不回来。存量脏数据用
`engine/examples/user_dict_clean.rs` 的判据二清理（放行打一半 / 简拼 / 缩写后缀）。

### 6.2 热度模型

| 档 | 判定 | 排序效果 |
|----|------|---------|
| 热词 | 7 天内使用 ≥ 2 次（`HOT_THRESHOLD=2`, `HOT_WINDOW_SECS=7天`） | 用户词层内优先 |
| 温词 | 7 天内使用 1 次 | 排在系统词之前 |
| 过期 | 超过 7 天未使用 | 仍保留，但不享受热度优先 |

数据模型：`user_dict(pinyin, word, frequency, last_used)`，主键 `(pinyin, word)`，重复学习累加频率并刷新 `last_used`。

### 6.3 生效路径（关键）

学习写入后必须**在排序上真的生效**，由 `user_rank` 维保证：

```
select_candidate → learn(pinyin, word)
    → user_words 集合 + user_index 前缀索引
    → 下次 query 命中（P1 层）
    → apply_word_len_match 的 user_rank = 0
    → 压过 common_rank=0 的系统常用词
```

**历史缺陷**（2026-11-17 修复）：排序键缺少 `user_rank` 维时，学过的词排在常用词表之后——学「种果」后 `zhongguo` 首位仍是「中国」。单字看起来正常，是因为单字不参与常用词加权。

## 七、搭配证据（前文参与）

### 7.1 四源取最大

`last_committed`（最近上屏的普通中文词）非空且 `context_enabled` 时，为每条候选计算搭配 lift，四个来源**取最大值**（不相加，避免同一份共现被计两遍）：

| 来源 | 权重范围 | 说明 |
|------|---------|------|
| 学习表 `context_pairs` | 累计次数，受 `context_weight_cap` 上限 | 用户实际共现 |
| 离线先验 `context_prior` | 1-6 档 | 语料统计，冷启动用 |
| 内置精选表 `context.rs` | `context_builtin_weight` 可配 | 人工维护的强搭配 |
| 档位表 `bigram.db` | 1-6 档 | 与离线先验同源，供拆组与主排序共用 |

### 7.2 档位语义与证据门槛

档位定义（统计侧 `build_context_prior.py`，绝对频次映射，**不按分位切分**）：

| 档 | 共现次数 | 主排序是否生效 |
|----|---------|---------------|
| 1 | 1 次 | ❌ 视为无证据 |
| 2 | 2-3 次 | ✅ |
| 3 | 4-7 次 | ✅ |
| 4 | 8-15 次 | ✅ |
| 5 | 16-39 次 | ✅ |
| 6 | ≥40 次 | ✅ |

**规则：档位 1 不计入主排序**（视为无证据），2 档起才提升。消费侧判据是 `lift >= 2`。

两条历史教训（都来自实测，不是推断）：

1. **分位映射会把强数据错判成弱数据**。原实现按共现次数的分位切 6 档，共现 8 次也可能落到档位 1，被当成噪声丢弃。改为绝对频次后同一批语料的可用对从 5,453 涨到 43.6 万。
2. **"降档"不能替代"剔除"**。曾尝试把噪声对从高档位降到档位 2，结果：档位 2 仍然生效，碎片只是从高档位搬到了低档位——档位 2 的异常率从 10% 升到 50%，体积还涨了 37%。**同轮只命中一个候选时，档位 2 和档位 6 的效果一样**，低权重不等于不生效。

### 7.3 清洗口径（统计侧强制，2026-11-17 落地）

纯语料统计会引入两类系统性噪声，实测异常率达 36%，必须在统计侧过滤：

| 规则 | 作用对象 | 依据 |
|------|---------|------|
| 双单字对整对剔除 | 两侧都是单字的对 | 单独抽 20 条，18 条不可用；档位 6 里双单字占 28.8%（最强档位掺入最多碎片） |
| 后词单字且非虚词 → 剔除 | 约 10 万对 | 清掉「马尔马→拉」这类专名尾字；虚词单字保留（拆组需要） |
| 前词单字且词频 < 3600 → 剔除 | 约 2 万对 | 清掉「芬→王朝」「政→收入」这类专名首字；`他/我/年/月/们` 不受影响 |
| `WEAK_NEXT` 扩到 38 字 | 档位 2/3 的弱搭配 | 补入 不/有/之/皆/其/亦/且/则/者/所/矣/焉/乎/已/于/此/各/该/并 |

前词单字词频门槛 3600 是实测分档，不是拍脑袋：碎片单字落在 2098–3457（芬 2098、政 2991、式 3457），常用单字落在 3880–4711（们 3880、他 4711），两档之间有空档。

**根因说明**：碎片不是分词算法的问题，而是**词库本身收了专名碎片**（`马尔马`/`大维`/`楚考烈` 都在 `system_dict` 里，而完整词 `马尔马拉海`/`楚考烈王` 不在）。正向最大匹配如实切出了词库里的碎片。

**但第 4 轮实测修正了一个关键假设**：碎片不只是噪声，它们还是**长词在分词里的唯一入口**。给统计侧加排除规则后，碎片对确实从 3,556 对（0.92%）降到 0，但 120 例效果从 95 掉到 91——掉的是 `北丐洪+七公`（北丐洪七公，词库无）、`恨不相逢+未嫁`（7 字，词库无）、`国民生产+总值`（7 字在库但超 4 字分词窗口）这类。**删碎片 = 同时删信号。**

所以正确方向不是"绕开碎片"，而是**补长词**（用碎片的高频跟随字在语料里还原完整词形后入库）。碎片问题会在长词补齐后自然消解。

### 7.6 前缀补全（Completion）—— 已实现

**状态**：已实现（2026-11-17，`48eeed1` / `102a347`）。完整实现记录见
[COMPLETION-IMPL.md](COMPLETION-IMPL.md)。

**实现前后**（`probe_prefix`，1,170 条真实输入留痕，冷启动）：

| 场景 | 实现前 | 实现后 |
|------|-------|-------|
| 打满全部音节 | 98.7% | 98.7%（不退化） |
| **只差一个音节** | **4.8%** | **37.8%** |
| 只打第一个音节 | 2.0% | 34.1% |

「打满 98.7%」只能算及格线——那是输入法的底线要求，不是竞争力。

**根因不是"没有前缀匹配"**：`dictionary::query` 本身就是前缀查询，`lian` 返回 3,117 条
（「联系」在词库顺序第 6、「联合」第 7、「连续」第 10）。问题是 `apply_word_len_match` 的分组：

- 输入 `lian`（1 音节）→ `counts = [1]`
- 单字（两/连/脸）→ group 0
- 多字词（联系/联合）→ group 2（字数 > N）

前 5 全是 group 0 的单字，completion 候选永远进不来。`tong` 的前 5 是「同/通/统/铜/痛」，
而「通常」在词库第 8 位。

**实现要点**（细节与踩坑见 [COMPLETION-IMPL.md](COMPLETION-IMPL.md)）

候选来源新增 `Source::Completion`，分组改四级：

| group | 内容 | 判据 |
|-------|------|------|
| 0 | exact | 字数 == N |
| 1 | **completion** | `source == Completion`（排在 exact 之后、偏短/偏长之前） |
| 2 | shorter | 字数 < N |
| 3 | longer | 字数 > N，非 completion |

`combo_like` 维把 Completion 判 0——它来自词库前缀，是真实词条，不是拼出来的串。

**四条判据，每条都由实测逼出来**：

1. 输入停在完整音节边界（`is_complete_pinyin`）——`lian` 是，`lianx` 不是
2. 候选拼音**只多一个音节**：剩余部分切一刀后必须为空。
   `lianxi`（剩 `xi`）通过；`liang`（剩 `g`）被挡——它是字符前缀，
   放进来就是「两/量」噪声。多音节扩展（`zhongguo` → 中国奥委会）也挡掉
3. 候选是多字词——单字由精确段负责
4. **已打满不展开**：精确段前 5 存在「字数 == 输入音节数」的多字词时直接跳过。
   缺这条时打满命中率从 98.7% 掉到 96.2%

**排序位置**：词长分区之后、隔音歧义提升之后、置顶之前。

- 分区之后：需要精确候选先排好，才知道「保留前几位」
- 隔音歧义之后：`lian` 同时是 `li+an`，隔音歧义会把「凉了」插到第 5 位抢掉补全的坑
- 置顶之前：用户显式置顶的词仍应压过补全

**插位而不是分组**：`lian` 的精确段有 32 个单字，任何「排在全部精确候选之后」的位置
都是第 33 位。改为「保留前若干位精确候选，补全紧随其后」。

**保留位数按「空间 + 常用词」取大**（2026-11-17 修正）：

| 组成 | 取值 |
|------|------|
| 空间分配 | `page_size - 4`，钳制 1..=5（留 4 个补全位） |
| 常用词覆盖 | 精确段前 `page_size - 1` 位中**最后一个**在常用词表内的位置（跨过中间的非常用字） |
| 最终 | 两者取大，上限 `page_size - 1`（至少给补全留 1 位） |

为什么必须加「常用词覆盖」：只按空间算时，9 位窗下 `shi` 前 5 是 是/时/使/事/市，
补全占满第 6-9 位，「十」（常用词表 rank 11）被整片挤出首屏。`first_char_verify`
全量在 9 位窗实测 **21 个常用词不在第一屏**（十/骑/演/几/袭/静/相/误/亲/兼/舰/蹑/氢…），
全是这条。改为常用词覆盖后降到 **3 条**，剩余三条是独立缺陷（见 10.2）。

取「最后一个」而不是「连续前缀」：`nie` 的精确段是 捏/聂/孽/镍/?/蹑，中间的非常用字
会让连续计数提前断在第 4 位，蹑仍被挤出去。

**5 位窗的取舍**（实测，2026-11-17）：首屏 5 位放不下「常用单字」与「补全」两样。
采纳「保常用字」——原实现 273 个常用词不在第一屏（占 2,732 条的 10%），
这个缺陷比补全命中率下降 8pt 更严重（打满场景是底线）。

| 5 位窗方案 | 只差一音节 | 常用词不可见 |
|-----------|-----------|-------------|
| 原实现（保留 1 位） | 37.8% | 273 |
| 保常用字（保留 ≤4，补全留 1 位） | 29.8% | 42 |
| **保常用字（保留 ≤5，补全退第二页）** | **26.7%** | **21** |
| 不插补全 | 3.4% | 22 |

采纳「保留 ≤5」：5 位窗前 5 个坑全给单字，补全退到第 6 位（第二页首位，翻页可达）。
`exam` 用例 26/26 通过（保留 ≤4 时 `ji` 的「急」、`wu` 的「武」落榜）。

**词频序来自词库，不来自候选原序**：`completion_candidates` 返回的列表是收集后统一
排序的（用户词 > 常用词 > 系统词 > 领域词，层内词频降序）。不能按 `BTreeMap` 的
拼音字典序遍历直接取——`liana`/`lianb` 段的生僻词会占满名额。

**验收**（2026-11-17，保留位修正后）

| 指标 | 5 位窗 | 9 位窗（平台默认） |
|------|-------|-------------------|
| 打满全部音节 | 98.7% | 99.1% |
| 只差一个音节 | 26.7% | 35.9% |
| 只打第一个音节 | 23.0% | 31.4% |
| `first_char_verify` 全量 | 21 / 2732 | **3 / 2732** |
| `exam` 用例（26 条） | 26 / 26 | 26 / 26 |

- `check_first` 0 FAIL / 9 WARN（不变）
- `probe_context` 95 提升 / 25 不变 / 0 变差（不变）
- lib + 集成测试 383 passed（必须 `--test-threads=1`，全局词库单例并发会假失败）

## 九、诊断工具

排障与验证不靠猜，靠探针。全部在 `engine/examples/`，`cargo run --release --example <name> -- <参数>`。

| 工具 | 用途 | 用法 |
|------|------|------|
| `probe_rank` | **三层对照**：词库原始顺序 / 整句解码结果 / 最终候选 | `-- youxianji` |
| `probe_prefix` | 渐进式命中：真实输入留痕的「打满 / 只差一音节 / 只打第一」首屏率，输出未命中样本 | `-- <tsv> [--page-size 9]` |
| `probe_candidates` | 批量输入的前 8 候选 + 中英构成 | 无参跑内置 30 例；带参测指定输入 |
| `probe_learn` | 学习是否真的生效（选词后二次输入是否升首位） | 需隔离 APPDATA |
| `probe_context` | 搭配表效果：多档位门槛对比 + 人工注入验证链路 | 无参 |
| `check_first` | 全音节首屏体检：常用词不在首屏（FAIL）/ 首屏含生僻字（WARN） | 无参，409 音节 |
| `probe_sentence` / `probe_span` / `probe_combo` | 整句解码 / 格子缓存 / 逐音节组合 | 按需 |
| `probe_split` | 词库查询的分段（精确段长度 / 前缀扩展）与补全候选 | `-- lian tong xian shi` |

**排障决策树**（按顺序，别跳步）：

1. 词库里有这个词吗？→ `probe_rank` 看「词库原始顺序」
2. 是整句/组合拼出来的吗？→ 同上看「整句解码」
3. 排序链把它降组了吗？→ 对比「原始 vs 最终」的位次差
4. 学习没生效？→ `probe_learn`（注意样本必须是同拼音词库词，纠错来源按设计不学）
5. 首屏被生僻字占？→ `check_first` 的 WARN 段

## 十、已知缺口与演进方向

### 10.1 已修（2026-11-17 校准）

| 问题 | 根因 | 修法 |
|------|------|------|
| 整句产物压过真实词条 | 整句候选在排序链**之后**插入 | 前移到排序链之前 + `combo_like` 维 |
| 学过的词不生效 | 排序键缺 `user_rank` 维 | 补维，用户词优先于常用词表 |
| 搭配档位 1 制造随机重排 | 98.6% 数据是单次共现，仍计入 lift | 档位 1 不计入主排序 |
| 分位映射把强数据判成噪声 | 按共现次数分位切 6 档，共现 8 次也落到 1 档 | 改绝对频次映射，可用对 5,453 → 436,545 |
| 搭配表 36% 是分词碎片 | 双单字对（11.4%）+ 后词单字专名尾字；档位 6 里双单字占 28.8% | 双单字剔除 + 后词单字非虚词剔除 + 前词单字低频剔除 → 异常率降到 6% |
| 碎片降权以为能改善搭配表 | 降权不改分词（`load_vocab` 只看词长不看词频），重跑结果逐条相同 | 认知修正：碎片是长词的分词入口，删碎片同时删信号；方向改为补长词 |
| 组词首位是整词导致数字透传 | 选中整词即 `compose_idx` 到头，组词结束 | 首位固定当前音节单字 |
| 8 个音节首屏混入生僻字 | 常用词表无该音节条目 | 补 29 条常用字 |
| 前缀补全缺失（打 `lian` 出不来「联系」） | 精确段 32 个单字把补全候选压到第 33 位；补全候选在词库扩展段里没有身份 | 新增 `Source::Completion` + 前部插位（见 7.6）：只差一个音节 4.8% → 37.8% |
| 9 位窗补全插位挤掉常用单字 | 保留位只按空间算（`page_size - 4`），精确段第 6 位起的常用字被补全整片挤出首屏 | 保留位改为 max(空间, 精确段内最后一个常用词位置)：9 位窗常用词不可见 21 → 3 |

### 10.2 仍存在的缺口

1. **分词窗口与语料的匹配**（第 5 轮实测再修正）：第 4 轮判断「补长词能根治」，第 5 轮证否——补 100 条长词后碎片对只降 **0.65%**（3,556 → 3,533），120 例持平 95。根因是三重叠加：
   - 分词窗口只有 4 字（`WORD_MAX_LEN`），补入的 100 条里 **43 条是 5-8 字，根本没进分词词表**
   - 进了词表的 57 条也大多没改变切分（搭配表只变动 9 对：385,983 → 385,992）
   - 放宽窗口到 8 字已验证会掉效果（120 例 95 → 93）
   
   **结论：搭配表的质量瓶颈在分词口径，不在词库覆盖率。** 继续补长尾长词边际收益接近零。长词补充仍有独立价值——用户能打出专名（`马尔维纳斯群岛`、`仙剑奇侠传` 抽测 7/7），所以 `curate/longwords.txt` 保留为「按需补词通道」。
2. **语料归档（已完成）**：5 万页语料（201 MB / 4 片）已跨盘备份至 **`D:\taishendictback`**。`zhwiki-latest` 是滚动快照，这份分片是**唯一能精确复现当前 385,983 对的输入**——重新下载的 dump 内容已变，只能"重新统计一个同量级的表"而非复现。`taishen-dict/tmp/corpus_50k_full/` 仍可作工作集，但归档以跨盘那份为准。
3. **单字只有词库词频**：没有"单字使用热度"独立数据，`shua` 这类音节的首屏完全依赖词库词频序。
4. **常用词表规模有限**：2732 条 + 495 单字。未覆盖音节仍退回词库词频。
5. **候选无显式分数**：候选结构体是 `{ text, source }`，没有 `score` 字段。当前靠"分区 + 字典序比较"实现，可解释性好，但无法表达"两维同时接近"的近似比较，也无法做跨阶段统一打分。
6. **学习别名治理**：历史上同一词攒出多种拼音别名（已限制为只学完整拼音，存量需工具清理）。
7. **权重上限 6 相对词频差偏小**：实测有案例搭配成立但仍被词频差压住（`耶稣→基督`、`由来→已久`、`礼部→尚书`）。属调参范畴。
8. **`first_char_verify` 剩余 3 条**（9 位窗，2026-11-17）：均为独立缺陷，与补全插位无关——
   - `bzhan` → b站：混合简拼（英文 `b` + 拼音 `zhan`）解析不出来，候选全是 zhan 系词
   - `alipay` → 支付宝：纯英文串没有中文别名映射（词库缺数据）
   - `ming'ri'yu'an` → 明日预案：隔音符没被当作强制音节边界，被解析成 3 音节 `ming ri yuan`
