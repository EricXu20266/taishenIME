# 长句候选质量诊断（2026-11-21）

> 对象：整句输入（12-30 音节）的候选生成与排序
> 方法：自建 270 条长句用例（90 句 × 全拼/虚词简/全简），冷启动环境（无用户词库、无学习搭配）
> 前置：排序 v2 已落地，短词用例 277/292

## 一、结论摘要

**冷启动长句通过率**（top1 必须完全命中）：

| 模式 | 通过 | 通过率 |
|---|---:|---:|
| 全拼 | 22/90 | **24.4%** |
| 虚词简（虚词取声母） | 10/90 | 11.1% |
| 全简（全声母串） | 0/90 | 0.0% |
| 合计 | 32/270 | 11.9% |

**放宽到「答案进前 9」也只有 35/270 = 13.0%**——只多 5 条。

这条数据决定了后续所有判断：**问题不在排序，在候选池里根本没有正确答案**。235 条长句连前 9 个候选都进不去。

## 二、根因（按贡献排序）

### 1. 同音字选错，占失败的 49.8%

240 条失败共 434 处替换，其中 **216 处是同音替换**。

关键发现：**16 组常见同音字对，16 组全部是「正确字词频更低」**：

```
再(3989) vs 在(4929)     词(3160) vs 此(3887)
改(3336) vs 该(3739)     例(2892) vs 力(3390)
升(3096) vs 省(3764)     键(2442) vs 见(4011)
杯(2884) vs 被(4228)     收(3292) vs 受(3709)
晚(3165) vs 万(3757)     聊(2452) vs 辽(3001)
半(3291) vs 办(3374)     字(3623) vs 自(3801)
交(3178) vs 叫(3899)     伞(2544) vs 三(3892)
雨(3067) vs 与(4378)     得(4312) vs 的(4627)
```

**只要按单字词频排序，这些字必然选错**——虚词词频天然高于实词。

### 2. 未登录组合出不来

典型：`wogangdaojiajintiantaileile` → 「我钢刀家今天太累了」，正确应为「我刚到家今天太累了」。

数学原因在 `sentence.rs` 的 `step_score`：

```
step_score = freq / 365.0 - 17.944

刚   3359 → -8.74
到   4467 → -5.71
刚+到     = -14.45   （两个词，扣两次 17.944）
钢刀 2019 → -12.41   （一个词，扣一次）
```

**「每个词扣一次 17.944」导致多切一个词的代价约 6549 词频**。所以系统宁可输出生僻词「钢刀」，也不肯拆成两个常用字「刚+到」——因为差 742 词频，翻不过来。

### 3. 搭配表覆盖偏斜

`bigram.db`（`context_prior` 表）38.6 万条，内容以书面语名词短语为主。

```
刚 → 到    无        再 作为 next：0 条前驱
太 → 累    无        在 作为 next：10,654 条前驱
词 作为 next：0 条    此 作为 next：492 条
```

**「再」「词」「改」这类字在搭配表里一条前驱都没有**，而「在」「此」「该」有大量。所以任何基于搭配表的加权都会进一步强化错误方向。

## 三、已证伪的方案（都实测过，勿重复）

| 方案 | 做法 | 结果 |
|---|---|---|
| **补词条** | 合并 9,823 条口语词（含 2,017 条 conversation 域） | 30/270 → 30/270，**零提升** |
| **开语言模型**（旧结构下） | 接入 52.3 万词 + 458 万 bigram | 30 → 32，+2 条（在噪声内）。**结构修复后重测为 +13.3 点，见第七节** |
| **调大 bigram 权重** | `BIGRAM_W` 1.2 → 1.75 | 长句 +2，但主用例 L4 从 68 → 66，**净效果接近零** |
| **调 learned_context_cap** | `tuning.json` 设 64 | **零变化**——`ffi.rs:214` 硬编码 `load_context_pairs(2, 8)`，该配置项根本不生效 |
| **带自学习测试** | 加载真实用户词库（4,998 词 / 18,622 搭配） | 仍 30/270，**零提升**；且产品视角本就不该依赖个人学习数据 |
| **通用口语搭配语料** | LLM 生成 340 条真实搭配并入 bigram.db | 32 → 30，**反向退化** |

### 语料工程失败的原因（重要教训）

试点语料按「真实语言分布」写，结果如下：

```
我们 → 在   我给 count=6
我们 → 再   我给 count=3
```

**这在统计上是对的**（「我们在」确实更常见），但它**恰好强化了错误方向**。按真实分布造语料，等于重造一份同样偏斜的数据。

**结论：语料必须按「目标场景」定向，不能按「通用分布」生成。**
目标场景是即时通讯（「我们再说」「再看一下」），不是通用书面语。

## 四、方法论提醒（下次对比必须注意）

**测试存在 ±1 条波动**：同一份数据、同一套用例，恢复备份后重跑，全拼从 22/90 变成 21/90。

推测原因：`bigram.db.bin` 重建后索引顺序变化，影响同分候选的 tie-break。

**所以**：
- 单次 ±2 条以内的差异**不能作为改进依据**
- 做对比必须固定 bin 缓存，或跑 3 次取多数
- 之前记录的「+2」「-2」结论中，有一部分可能就在噪声里

## 五、剩余可行方向

### A. 场景定向语料（未验证）

按即时通讯语感重写搭配语料，强制覆盖「再说/再看/再聊/再等等」这类表达。
**风险**：即使定向，「在」的天然高频仍可能压过「再」，收益不确定。

### B. 候选易选性（未验证）

不追求 top1 必对，改为保证正确答案稳定出现在前 3-5，配合数字键快选。
技术确定性强，但要改交互设计。**当前 top9 只有 13.0%，这条路的前提也不成立**——先把 top9 提高才有意义。

### C. 结构性：放宽切词惩罚（未验证）

`step_score` 的常数惩罚 17.944 是「宁可成词不拆碎」的设计取向。若按音节位置动态调整（首末位置宽松、中间收紧），可能让「刚+到」有机会胜出。
**风险**：影响所有句子，需要全量回归。

## 七、2026-11-22 修复记录（本文档结论的更新）

### 修了什么

| 层 | 修复项 |
|---|---|
| 解码结构 | `char_graph` / `viterbi` 每条边保留最优与次优**两位独立前驱**，不再让高频无歧义边把前序束宽压成 1（束塌缩）；整句候选条数不再硬编码 3 条 |

### 参数矩阵（4 组对照，用于分离「结构」与「参数」的贡献）

| 组 | SPAN_TAKE / BEAM_WIDTH / ABBREV_BUDGET | LM | 全拼 | 虚词简 | 延迟峰值 |
|---|---|---|---:|---:|---:|
| A（当前默认） | 8 / 12 / 256 | 开 | 40.0% | **34.4%** | 97 ms |
| B | 6 / 8 / 32 | **关** | 27.8% | 10.0% | 90 ms |

三条结论：

1. **参数几乎不花钱**——四组延迟全在 90±7 ms，差异在噪声内。选参数应看准确率，不必为性能妥协。
2. **语言模型是主力**——全拼 B(关)27.8% → C(开)41.1%；虚词简 10.0% → 24.4%。
3. **参数按场景分工**——放宽只对虚词简有用（24.4→34.4），对全拼甚至有害（41.1→40.0）。

### 对第三节的修正

「开语言模型无效」的结论**只在旧结构下成立**。旧结构的束塌缩让语言模型的提升无处发力——候选路径在打分前就被剪掉了。结构修复后，同一份模型贡献 +13.3 点。

**教训：任何「某数据/模型无效」的结论，都要标注它依赖的代码结构。结构变了，结论要重测。**

## 八、长输入延迟定位（2026-11-22）

### 归因边界（先划清责任）

长输入（≥5 音节）单键峰值 40–97ms。**该延迟在本次改动前已存在**——HEAD 版本 `zhongguorenmin` 峰值 81ms，本次改动只增加 5–15ms。这是既存问题，需独立专项。

### 已排除的 8 个嫌疑（全部实测，勿重复）

| 嫌疑 | 实测数据 | 结论 |
|---|---|---|
| 词库跨度查询 `span_candidates` | 200–900us（全串所有子串合计） | 不是 |
| 多音字提示 `word_hints` | < 5us | 不是 |
| 纠错候选 `near_syllables` | 2–23us | 不是 |
| 语言模型查询（`TS_LM_OFF` 对照） | 38.7ms vs 36.3ms | 不是 |
| 容错切分预算（20000 → 3000） | 35.7ms vs 35.5ms | 不是 |
| 缓存冷热（同一输入连跑两遍） | 39.9ms vs 42.5ms | 不是 |
| 束剪枝 `prune_at` / `backtrack` | 15–108us | 不是 |
| 边打分 `push_top_two_preds` | 0.6–2.5ms（占 5–26%） | 不是 |

### 已测部分只覆盖 5%

`zhongg`（6 字符）`char_graph` 实测 34–47ms，其中已测量的 `near`(18us) + `prune`(53us) + `push`(1.7ms) ≈ **1.8ms，占 5%**。剩余 95% 散布在循环体的分配与构造中。

### 反直觉现象（最有价值的线索）

```
zhongg         125 个节点   34–47 ms
jintiantianqi  602 个节点    2.3 ms      ← 节点多 5 倍，却快 15 倍
```

**节点少反而慢**。说明瓶颈不在节点数，而在「跨度组合 × 每段候选」的路径构造——短输入无法精确切分时，每个起点都要尝试长跨度组合。

## 九、常驻内存实测与首次瘦身（2026-11-22）

### 实测账目（`TS_MEM_REPORT=1`）

```
system_dict   index 232 / short 44 / suffix 65 / full 39 / short_full 30 / trad 21  = 433 MB
domains       dom_index 242 / dom_short 67 / dom_full 20 / dom_exact 18 / word_domain 7 = 356 MB
保守合计      789 MB   实际峰值 1290 MB（哈希桶冗余约 60%）
LM 增量        40 MB
```

### 根因

索引全部是 `HashMap<String, Vec<(String, u32, ...)>>` / `BTreeMap<String, Vec<(String,u32)>>`——**每个前缀一个独立 String key，每个词条在每个前缀下各存一份 String**。

领域词构建处（`build_domains_from_db`）：

```rust
for i in 1..=pinyin.len() {          // 逐字符建前缀
    data.domain_index.push(&pinyin[..i], (word.clone(), ...));
}
```

「三维计算机图形」这一条词，会在 21 个前缀下各存一份。**17.6 万领域词因此产出 108 万前缀、242 MB**——和主词库（37 万词 / 107 万前缀）几乎同规模。

### 首次瘦身：领域词前缀按音节边界落点

改成只落「音节边界 + 完整拼音」：`sanwei`、`sanweijisuanji`、`sanweijisuanjituxing` 命中，中间的 `sanweij` 不建。

| 指标 | 改前 | 改后 | 变化 |
|---|---:|---:|---|
| dom_index keys | 1,082,004 | 383,184 | **-65%** |
| dom_index 内存 | 242 MB | 80 MB | **-162 MB** |
| 领域索引合计 | 356 MB | 194 MB | -162 MB |
| domains.db.bin | 171.6 MB | 93.5 MB | -45% |
| 稳态峰值 | 1290 MB | 1140 MB | **-150 MB（-12%）** |

功能验证（全部正常）：

```
sanweijisuanjituxing → #1 三维计算机图形   （完整拼音走 domain_full_index）
sanwei                → #2 三维             （完整音节前缀走 domain_index）
wb                    → #1 微博             （简拼走 domain_short_index）
ludixunyangjian       → #1 陆地巡洋舰
```

主用例集 278/292（改前 277/292），长句全拼 36/90、虚词简 31/90，**零回归**。

### 剩余大头与下一步

瘦身后仍是 1140 MB，主因：

- `system_dict.index` 232 MB（107 万前缀，核心索引，不能按领域词同样方式截断——用户会在任意位置补全）
- `system_dict.suffix` 65 MB（每值两个 String）
- `dom_short` 67 MB（领域简拼索引，同样是逐字符建）
- 哈希桶冗余约 60%

**下一步候选**：`dom_short` 同样改音节/字母边界（约 -30 MB）、`suffix` 合并字符串（约 -30 MB）、mmap 零拷贝（约 -70%，大工程）。
