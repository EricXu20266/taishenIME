# 笔形辅码（智能ABC 音形）数据层验证 — 2026-10-31

> 触发：终端用户反馈「打 hang7 时 7 直接选第 7 个字上屏」，期望 `hang7` 过滤出「杭」。
> 范围：只验证数据层（能否稳定产出「汉字 → 笔形码」），不涉及引擎与按键改动。
> **状态：暂不实现**（2026-10-31 决策）。本文保留验证结论与数据选型，供以后重启该功能时直接复用，不需要重新调研。

## 一、需求原形

智能ABC 的笔形码是八类：1 横、2 竖、3 撇、4 点捺、5 折、6 弯、7 十字交叉、8 方框。

「杭」= 木（交叉 → 7）+ 亢；「吴」= 口（方框 → 8）+ 天；「长」= 首笔撇 → 3。

智能ABC 之所以能「拼音后直接跟数字」，是因为它**输入阶段不出候选窗，按空格才出候选**，数字在编码阶段只属编码。泰深是实时候选模型，数字键固定为选字（`platform/windows/src/tsf_keyevent.cpp:731`），所以冲突来自交互模型，不是键位映射。

## 二、参考调研结论

| 参考 | 结论 |

业界没有「数字既当码又当选字」的既成做法：所有辅码方案要么换键位（字母码 + 非数字触发），要么换交互模型（智能ABC 空格出候选）。

`radical_pinyin` 未采用的原因：它是**音形反查码**，同一部件有多种读音标注（目 → `wei'er`/`kou'er`/`guo'er`），且混入笔形描述（口 → `shu'zhe'heng`），读音与字形多对多，不能直接生成笔形码。

## 四、方法

两层：

1. **IDS 取首部件**：`杭 = ⿰木亢`、`吴 = ⿱口天`、`想 = ⿱相心`（首部件「相」再拆得「木」）。覆盖 hanzi-writer 9575 字的 99.9%（9569 字）。
2. **部件 → 笔形类映射表**：每个部件只判一次，表规模远小于逐字判定。直接首部件 925 种，其中 785 种可由几何法自动给初稿，140 种需补录。
3. **几何兜底**：无 IDS 拆解的独体字（长、月、用、目、田）与表外部件，用 `medians` 做逐笔分类（横/竖/撇/点捺/折）、横竖中段相交判交叉、四边覆盖 + 端点闭合判方框。

## 五、结果

全量 9575 字中，**9457 字（98.8%）可算出笔形码**，118 字无码（多为生僻部件、IDS 未收字）。

样例验证（IDS 首部件 + 初稿表）：

| 字 | 码 | 推导 | 对错 |
| --- | --- | --- | --- |
| 杭 | 7 | 杭 → 木 | ✅ |
| 吴 | 8 | 吴 → 口 | ✅ |
| 长 | 3 | 独体，几何兜底 | ✅ |
| 想 | 7 | 想 → 相 → 木 | ✅ |
| 妈 | 5 | 妈 → 女 | ✅ |
| 村/桥 | 7 | → 木 | ✅ |
| 说 | 4 | → 讠 | ✅ |
| 明 | 8 | → 日 | ✅ |
| 同 | 2 | 同 → 𠔼 → 冂 | ✅ |
| 国 | 2 | → 囗（表内条目错，应 8） | ❌ |
| 回 | 2 | → 囗（同上） | ❌ |
| 月 | 2 | 表内条目错（应 3，撇） | ❌ |
| 的 | 5 | → 白（表内条目错，应 3） | ❌ |

初稿表前 40 条人工核对，错 9 条（扌、忄、月、虫、糹、衤、鱼、魚、禾），约 **77% 初稿准确率**。错误集中在三类：

- 交叉判定过激：禾（撇开头）被判 7，扌（真交叉）漏判
- 方框判定过激：虫、糹、衤、鱼、魚 被判 8
- 竖撇不分：月、忄 首笔被判竖

失败样例的共同点：初稿来自几何分类，而「竖撇 / 方框 / 交叉」在笔画中轴线上本身不可分。**架构没问题，错在初稿条目**——每个部件的码是固定映射，人工确认一次即可。

## 六、结论

数据层能撑住。

- 覆盖率 98.8%，剩余 1.2% 为生僻字，可用手工补录兜底
- 需要的人工资产是一张 **925 条部件笔形码表**（其中 140 条需补码），约半天工作量
- 初稿误差集中在 20%~25% 的条目，人工校正后错误率可压到接近零（部件是离散映射，不存在逐字漂移）
- 独体字（长/月/用）无法靠 IDS 拆解，必须走表 + 几何，智能ABC 规则对「竖撇」本身没有客观口径，需先定产品口径
