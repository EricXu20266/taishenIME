## 背景：为什么会有碎片

搭配表三轮下来发现一个根因：**`system_dict` 里收了大量专名碎片**。

实测样本：

| 碎片 | 词表状态 | 词频 | 完整词是否在词表 |
|---|---|---|---|
| 马尔马 | 在（`maerma`） | 1189 | 马尔马拉海 ❌ 不在 |
| 大维 | 在（`dawei`） | 1681 | 屋大维 ❌ 不在 |
| 楚考烈 | 在（`chukaolie`） | 759 | 楚考烈王 ❌ 不在 |
| 临川 | 在（`linchuan`） | 1489 | 临川音系 ❌ 不在 |
| 中发 | 在（`zhongfa`） | 1449 | 中发表 ❌ 不在（「中发」另有他义，见下） |

分词时正向最大匹配如实切出了词表里的碎片，于是产生「碎片 + 尾字」这类错误搭配
（`马尔马→拉`、`屋→大维`）。

目前统计侧靠三重过滤绕开（双单字剔除 / 后词单字非虚词剔除 / 前词单字低频剔除），
代价是**被误伤的合法搭配无法进入搭配表**。清理碎片词条可以从根上解除这层限制。

## 关键约束（先读，这轮风险比前三轮高得多）

1. **动的是候选主体**。搭配表错了只是排序变差，词库错了用户直接打不出字。
2. **只降权，不删除**。方案是把碎片词条的 `frequency` 降到最低档（如 1），
   保留词条。理由：删除不可逆，而降权后该词条在所有正常词之后，
   用户翻页仍能取到，不会出现「打不出」。
3. **必须先产出清单、经确认再动数据**。第 1-3 阶段只读不写。
4. 所有改动在 `E:\AllinDeepSeek\taishen-dict`；`taishenIME\resources` 是单向同步的消费端。
5. **文档、代码注释、commit 说明中不得出现任何竞品/其他输入法名称**。
6. 动手前备份 `output/system_dict.db`。

## 现状数据（别用错判据）

```
总词条 372,733
freq < 2000 : 351,423 (94.3%)
freq 2000-3600 : 20,930
freq 3600-5000 : 379
freq >= 5000 : 1
2 字词 115,271（100,932 条 freq<2000）

```

**结论：词频不能作为碎片判据**。94% 的词条都在 2000 以下，401/253 这类值是档位不是真实频次。
唯一可信的判据是**语义 + 语料行为**。

## 第一阶段：语料跟随度分析（只读，产出候选清单）

### 算法

碎片的核心特征是**它几乎总是作为更长词的一部分出现**。用现有语料量化：

对每个候选词条 `A`（2-4 字、`freq < 3600`）：

1. 在语料（`tmp/corpus_50k_full/`，或备份 `D:\taishendictback`）里统计：
   - `n(A)`：A 独立出现（前后都是切句边界/非汉字）的次数
   - `n(A + X)`：A 后面紧跟同一个字 X 的次数，取最高频的那个 X
   - `n(Y + A)`：A 前面紧邻同一个字 Y 的次数，取最高频的那个 Y
2. 判定：
   - **前缀碎片**：`n(A+X) / n(A) > 0.9` 且 `n(A+X) >= 3`
   - **后缀碎片**：`n(Y+A) / n(A) > 0.9` 且 `n(Y+A) >= 3`
   - 两者都不满足 → 保留
3. 附带信息（用于二次判断）：
   - `A+X`（或 `Y+A`）是否在词库？在 → 更可能是碎片；不在 → 长词本身缺失
   - A 的总出现次数（过少则证据弱，标为"待定"）

**注意**：`n(A)` 的定义要谨慎。"独立出现"指 A 前后都不接汉字（标点、空格、
英文、数字、段落边界都算边界）。如果 A 在语料里只以 `A+X` 形式出现，
`n(A)` 可能为 0，此时用 `n(A+X)` 的绝对量作为证据。

### 产出

`tmp/fragments_candidates.tsv`，字段：

```
word	pinyin	frequency	total_occ	follow_char	follow_ratio	precede_char	precede_ratio	verdict	long_word_in_dict
```

`verdict` 取值：`prefix_frag` / `suffix_frag` / `standalone` / `insufficient`

按 `total_occ` 降序，输出统计摘要：各类判定各多少条。

**这一步只产出文件，不改任何数据。**

## 第二阶段：LLM 复核（仍不改数据）

语料跟随度会有误判——例如「中国」后面 90% 跟「人」或「政府」，但它当然是独立词。

**防线：加一条前置排除**——只有满足以下条件才进入 LLM 复核：

- 该词**不在常用词表**（`curate/common_dict.txt` 里的 2703 条）
- 该词**没有作为独立词的高频用例**（`total_occ` 里独立出现次数占比 > 20% 则直接判 standalone）

然后对剩余候选批量问 LLM（每批 50 条）：

> 下面这些中文词条，哪些**不能独立使用**、只是更长专有名词或术语的一截？
> 对每个词条回答：独立 / 碎片 / 不确定，并用 5 字内说明。

输入要带上语料信息（如「马尔马」后面 100% 跟「拉」），让 LLM 有依据判断。

**产出**：`tmp/fragments_llm_verdict.tsv`，字段 `word	verdict	reason`

**LLM 只处理"确定是碎片"和"确定独立"两类，"不确定"的一律保留**。

## 第三阶段：人工抽检（交叉验证）

从 LLM 判定为「碎片」的集合里抽 50 条，从「独立」里抽 20 条，人工核对。

**通过标准**：
- 「碎片」类抽检准确率 ≥ 90%（即 50 条里错判 ≤ 5 条）
- 「独立」类抽检不得有碎片（20 条里 0 条）

**不通过则停止**，回到第二阶段改 prompt 或调整语料跟随度阈值。
**不要靠扩大人工审核范围硬扛**——判据不稳就先修判据。

## 第四阶段：小批试点（首次写数据）

从确认无误的碎片里取前 200 条（按 `total_occ` 降序，影响最大的那批），执行降权：

```sql
UPDATE system_dict SET frequency = 1 WHERE word = ? AND pinyin = ?;
```

**同时记录原始频率到 `tmp/fragments_downgraded.tsv`**（word, pinyin, 原 frequency），
这是回滚依据。

然后：

1. 重建 `.bin` 索引（部署期由引擎生成，本地用 `cargo run --release` 前的构建链）
2. 重跑 `verify_build.py`
3. **重跑搭配表统计**（分词依赖词表，词表变了搭配表必须重算）
4. 验收：
   - 用 `probe_candidates` 抽测 10 个碎片所在拼音，确认正常词仍在首屏
   - 重跑 120 例 `probe_context`，提升数不得低于 95
   - 重跑 `check_first`，FAIL 必须仍为 0

**试点不通过就回滚，不要继续扩大**。

## 第五阶段：全量执行

试点通过后处理全部确认的碎片。分母以第一阶段清单为准，如实报告：
- 判定为碎片的条数
- 实际降权条数
- 保留条数（含"不确定"类）

## 验收标准

| 项 | 标准 |
|---|---|
| 抽检准确率 | 碎片类 ≥ 90%，独立类 0 误判 |
| `verify_build.py` | 通过（四张表 + bigram 自洽性） |
| `check_first` | FAIL = 0（常用词仍可达首屏） |
| `probe_context` | 120 例提升 ≥ 95（不因词表变化退化） |
| 搭配表碎片率 | 重跑后抽检 50 条，异常率 < 4%（当前是 4%） |
| 抽样打字测试 | 抽 10 个碎片词条所在拼音，正常词仍首位 |
| 回滚能力 | `tmp/fragments_downgraded.tsv` 完整记录原值 |
