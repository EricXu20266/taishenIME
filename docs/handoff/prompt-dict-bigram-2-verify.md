## 本次三件事

### A. 质量抽检（最优先）

**目标**：确认 43.6 万对里没有系统性噪声。

**方法**：

1. 按档位分层随机抽样：档位 2/3/4/5/6 各抽 10 条，共 50 条。
   抽样 SQL 示例：
   ```sql
   SELECT prev, next, count FROM context_prior
   WHERE count = ? ORDER BY RANDOM() LIMIT 10;
   ```
2. 逐条人工判定语义是否合理：`(prev, next)` 是否是一个中国人日常会连起来说的词对。
3. 记录成表：`prev | next | 档位 | 判定(OK/异常) | 备注`

**什么算异常**（判定时可参考自己打字的直觉）：

- 语法通但不是词：「优先级 → 县级」这类
- 百科模板残留：「年 → 出生」「总人口 → 为」这类（脚本已有 `NOISE_PAIRS`，
  但白名单不可能覆盖全部，需要人工兜底）
- 人名/地名粘连：某部作品的角色表、某地区乡镇列表
- 重复句式：某本小说的固定句式被反复统计

**通过标准**：异常率 < 10%（50 条里不超过 5 条）。

**若超过 10%**：不要在这一轮顺手清洗。只报告——把异常样本按类型归类，
说明可能来自哪类语料，交给下一轮决策。**验收与修复必须分开**，
否则改动后无法判断是"清洗起效"还是"抽样运气好"。

### B. 语料可复现记录

**这是当前最大的技术债**：43.6 万对是从某批语料统计的，但那批语料不在仓库里
（`sources/` 只有 `jieba.py` / `wiki.py` / `__init__.py`），也没有任何来源记录。
下次想增量更新或复现，只能重新找。

**动作**：

1. 查明这批语料是什么：翻 `taishen-dict/tmp/`、其他盘的备份、
   最近几个提交的时间线（`2b1ce89` 是 2026-11-17 1:06 改的脚本，
   同时间前后 `output/bigram.db` 被重建——语料应该在那前后处理过）。
2. 新建 `sources/README.md`，写清：
   - 语料来源（路径 / URL / 获取方式 / 版权许可）
   - 规模（文件数、总字数、覆盖领域）
   - 分词方式（当前脚本用系统词库正向最大匹配，不是 jieba）
   - **完整统计命令**（可复制粘贴，含所有参数）
   - 档位映射口径（绝对频次 → 1-6 档的具体边界）
   - 重建步骤（从语料到 `output/bigram.db` 的完整链路）
3. 如果语料确实已丢失：在 README 里**如实写明**
   "当前产物的语料已不可得，无法精确复现"，并给出补救预案
   （重新抓取的范围、预估耗时）。

**不要假装有语料**。写"语料已丢失 + 补救方案"比编一个来源有用得多。

### C. 扩大效果验证

**现状**：只验了 14 个案例（`engine/examples/probe_context.rs` 内置集），
13 例提升。样本太小，看不出分布特征。

**方法**：

1. 扩大挖案例样本到 100+ 个。挖案例脚本逻辑（可复用上一轮的）：
   - 从 `context_prior` 取 `count >= 4` 的对
   - 前词必须是其拼音的第一候选（否则自动化测试选不中）
   - 后词在同拼音 top6 内且非首位
   - 每个拼音只取一例，避免同音干扰
2. 输出 TSV 到 `tmp/context_cases.tsv`，格式：
   `prev_word \t prev_pinyin \t next_pinyin \t next_word \t rank \t tier`
3. 跑：
   ```
   cd E:\AllinDeepSeek\taishenIME\engine
   cargo run --release --example probe_context -- ..\tmp\context_cases.tsv
   ```
4. 统计三项：
   - **总提升率**（提升例数 / 总数）
   - **平均提升位次**（off 位置减 on 位置）
   - **按档位分组**的提升率（档位 6 vs 档位 2，看权重梯度是否合理）

**期望**：总提升率 > 70%，档位 6 的提升率明显高于档位 2（说明"强搭配提得多"）。

**若档位 2 和档位 6 提升率接近**：说明当前是"命中即提升"的二值行为，
档位精细度没体现出来。这是已知的架构限制（消费侧用分区重排而非分数累加），
不是本轮要修的——记录到报告即可。

## 条件触发：什么时候才需要「LLM 补长尾」

只有当本轮 C 项验证发现**某类前词系统性覆盖不足**时才启动，例如：

- 口语短语类前词（「这个」「那个」「就是」）后继覆盖少
- 行业术语搭配缺失（「协议」「接口」「增量」这类）
- 新词搭配完全没有

届时的做法见 `prompt-dict-bigram-2.md`（原计划那份），但目标要改：
不是"把总量提到 5 万"（已达成），而是"定点补某类前词"。
