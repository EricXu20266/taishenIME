> 产出：长词还原清单 + （经确认后）补入词库的长词 + 重跑的搭配表

## 背景：第 4 轮把问题重新定位了

第 4 轮原本假设「碎片是搭配质量的根因，清掉就好」，实测被证伪：

| 方案 | 搭配对 | 120 例提升 |
|------|--------|-----------|
| 基线（线上） | 385,983 | **95** |
| 剔除 6442 碎片 | 384,439 | 91 |
| 剔除碎片＋长词切分保留 | 384,574 | 92 |
| 分词窗口放宽到 8 字 | 383,286 | 93 |

碎片对确实从 3,556（0.92%）降到 0，但效果掉 3-4 例。掉的是：

```
北丐洪 + qigong → 七公      （北丐洪七公，5 字，词库无）
恨不相逢 + weijia → 未嫁    （恨不相逢未嫁时，7 字，词库无）
国民生产 + zongzhi → 总值   （国民生产总值，7 字在库但超 4 字分词窗口）
```

**结论：碎片不只是噪声，它是长词在分词里的唯一入口。删碎片 = 同时删信号。**

所以本轮目标不是清碎片，而是**把碎片对应的完整长词还原出来补进词库**。
长词入库后，正向最大匹配会优先切长词，碎片自然不再被当作入口。

## 目标

1. 从碎片清单还原候选长词（`马尔马→马尔马拉海`、`楚考烈→楚考烈王`）
2. 用「语料独立度 + 语义确认 + 人工抽检」三道验证
3. 验证通过的长词补入词库
4. 重跑搭配表，确认碎片对减少且 120 例效果不退化

# 阶段 1：还原与验证（只读）

## 1.1 还原算法

输入：`tmp/fragments_candidates.tsv`（第 4 轮产物，348,369 行；用其中的 `prefix_frag` / `suffix_frag` 共 6,442 条）。

对每个碎片 A：

**前缀碎片**（A 是长词的前段，如 `马尔马`）：向右延伸
```
for L in 1..=4:
    # 取语料中 A 后面紧跟 L 个汉字的完整串
    候选 = A + (语料里 A 后最高频的 L 个汉字)
    统计 候选 的：
      total_occ     — 总出现次数
      standalone    — 前后都是边界（标点/空格/数字/英文/段落）的次数
    记录 (候选, total_occ, standalone)
```

**后缀碎片**（A 是长词的后段，如 `大维` 之于 `屋大维`）：向左延伸，同理。

**选择规则**：在 L=1..4 的候选里，取满足 `standalone >= 3` 且 `standalone / total_occ >= 0.5`
且 `total_occ` 最大的那个作为还原结果。若都不满足，标记 `unresolved`。

**为什么用独立度而不是纯频次**：`马尔马` 后面跟「拉」的次数可能很多，但
`马尔马拉海` 单独出现（后面是标点）才是"这是一个完整的词"的证据。

## 1.2 语义确认

还原出来的串可能不是词（如 `马尔马拉+海` 是地名，但 `楚考烈+王` 是人名+称谓）。
对 `resolved` 的候选批量问 LLM：

> 下面每条是「某词的一部分」+「在语料里经常跟着的字」。请判断拼起来后
> **是否是一个真实存在的中文词或专名**。回答：是 / 否 / 不确定，并用 10 字内说明。

**只保留「是」**；「否」和「不确定」都归入 `unresolved`，不推进。

## 1.3 人工抽检

从 LLM 判定为「是」的集合里随机抽 50 条人工核对。

**通过标准**：准确率 ≥ 95%（50 条里错判 ≤ 2 条）。

不通过则停止，回头调 1.1 的阈值或 1.2 的 prompt，**不要靠扩大人工范围硬扛**。

## 1.4 阶段 1 产出

`tmp/longword_candidates.tsv`，字段：

```
fragment	direction	restored_word	total_occ	standalone	ratio	llm_verdict	final
```

`final` 取值：`accept` / `reject` / `unresolved`

以及统计摘要：

- 碎片总数 / 可还原 / 不可还原
- 还原后按字数分布（4 字 / 5 字 / 6 字 / 7 字以上）
- 抽检结果

**到此停下，回报摘要等确认。**

# 阶段 2：补入词库（确认后执行）

## 2.1 补词位置与拼音

**先读 `pipeline.py` 确认词条的入库路径**，不要猜。要点：

- 补充词条应落在 `curate/` 下的哪个文件（是新建 `curate/longwords.txt` 还是追加到现有文件）
- 拼音怎么标：用 `pypinyin`（项目已有依赖）还是词库反查
- 是否需要同步更新 `VERSION.json`

**拼音必须校验**：补完后跑一遍反查，确认「输入该拼音能命中该词」——
可以在 taishenIME 侧用 `probe_candidates` 抽测（例如 `maerma` 应能出「马尔马拉海」）。

## 2.2 小批试点

先补 100 条最高频的（按 `total_occ` 降序），然后：

1. 重建 `output/system_dict.db`
2. 重跑 `build_context_prior.py`（分词依赖词表，词表变了搭配表必须重算）
3. 验收（见下）
4. 通过后再补剩余部分

## 2.3 验收

| 项 | 标准 |
|---|---|
| `verify_build.py` | 通过（含 bigram 自洽 + 双单字为 0） |
| `check_first` | FAIL = 0（常用词仍可达首屏） |
| `probe_context` 120 例 | **≥ 95**（不得因补词退化） |
| 搭配表碎片对 | 抽检 50 条，碎片率应从 4% 下降；若不降反升，说明还原的词不完整 |
| 抽测打字 | 抽 10 个新补长词，输入其拼音，确认能出且排在合理位置 |
| 长词是否抢首位 | 抽 5 个含短词同音的案例（如新补 7 字词 vs 2 字常用词），确认短词仍首屏 |

**特别注意最后一条**：补进来的长词如果抢了短词的首位，会重演「过度联想」问题。
词长分区（`group` 维）应该能挡住，但要实测确认。

## 2.4 回滚

备份 + 记录补词清单。若验收不通过，回滚到阶段 2 之前的 `system_dict.db` 并停止。

## 必须回答的问题

完成阶段 2 后，如实回答：

1. **补进去的长词，让搭配表的碎片对减少了多少？** 从 3,556 降到多少？
2. **120 例效果有没有恢复或提升？** 第 4 轮的教训是碎片是信号入口，补长词应该能把这部分找回来——但可能找不回，因为长词的统计口径不同。找不回就如实说。
3. **这条路值得继续吗？** 如果补了 100 条长词，碎片对只降了 5%，说明长尾太长，全量补的边际收益低——这个结论也要敢写。
